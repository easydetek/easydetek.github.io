# 用 EDK60 桥接 EDV163-N-03 人存雷达——人体存在检测（有人/无人 + 静止/运动 + 三维坐标）

> **一句话**：一块 EDK60_VA 开发板 + 一颗 EDV163-N-03 60 GHz 人存雷达（插在 **H3** 插槽），
> **不用 USB 转串口芯片、不用装驱动**，把雷达按协议 V1.1 上报的二进制帧（UART **256000** 8N1、大端、**帧尾 `0x0A`**、
> **正文有转义**）经原生 USB 实时送到浏览器，把「有人 / 无人」「静止 / 运动 / 靠近 / 远离」和目标的 `x / y / z`（mm）
> 画成状态卡、距离门能量条、俯视散点与事件时间线。

**这套方案与站内另两套 EDV163 案例（[水位](./level-guide) / [挥手](./gesture-guide)）的关系**：同一块 EDK60_VA、同一个 H3 插座、
**同一份「纯字节双向透传桥」固件**（网页烧录页内置的就是它），差别全在两端——模组换成人存版 EDV163-N-03，
上位机换成解析《EDV163 替换 EDQ152 成品通用协议 **V1.1**》的 `0x81`（**每通道 9 字节**）与 `0x80`（40 距离门能量）。
所以照抄另外两套的**接线与烧录**没问题，照抄它们的**解析器与参数**就会错——尤其 `0x81` 的步长（9 B/通道）和上报节奏（默认 **5 s**）。

**这篇文章的证据边界要说在前面**：本文所有帧字节、校验和、转义后的线上字节都由脚本生成并逐字节复核（第 7 节给了可复现的组帧伪代码），
协议原文里 8 条示例帧（4 组，每组主机发送 + 设备响应）的校验和也逐条对上了。但**这套链路还没有在 EDV163-N-03 实物上跑过一条用例**——
因此正文里凡是「多少帧、多准、多久、准不准」的量化结论，**一律标着「待实测 + 判据」，一个实测数字都没有**。

## 1. 场景需求

人存检测要回答的问题只有一句：**这个空间里现在有没有人，人在哪，动不动。** 不同场景对这句话的容忍度完全不同——

| 需求场景 | 具体需求 | 本方案如何满足 |
|---|---|---|
| **卫生间有人** | 隔间里有人蹲着不动也要判「有人」；人走 10 s 内要能判「无人」，否则灯不灭 | `0x81` 的 `静止/运动` 状态位（0 无人 / 1 静止 / 2 运动）+ `0x11` 检测延时（把「保持有人」调到 3~10 s）；`0x81` 的 `z` 与 x/y 给出目标方位 |
| **会议室占用** | 判断「有会 / 空会」；空会后要能自动释放资源；区分「有人但安静坐着」与「真的没人」 | `0x17` 上报频率调到 1 s 拿到连续状态；`0x11` 延时决定释放速度；**必须用「静默超时」推断无人**（默认 5 s 上报 + 无人静默，见 6.4） |
| **工位在席** | 长时间（小时级）在席判定，要求「坐着不动 ≠ 无人」，且不能因为 30 min 规则被强制清零 | `0x1D`（30 min 强制无人）默认关，工位场景**应保持关**；`0x1C`（无人后持续存在检测）可用于「走后仍允许再触发」；静止判定依赖模组的静止目标能力（**静止识别率待实测**） |
| **停车位占位** | 非接触判断车位被占 / 空闲；车体是静止大目标，需抗雨雪与地面反射 | `0x81` 的 `presence` 位 + x/y（车位平面内的目标位置）；`0x27` 检测范围收窄到单个车位；`0x29` 屏蔽区挡掉相邻车位与立柱投影（**每帧最多 2 块，见 7.8**） |
| **投光灯 / 智能面板感应** | 触发要快、误触发要少；人站在灯下不动灯不能灭 | `0x24` 触发模式（0 正常运动触发 / 1 靠近 / 2 远离 / 3 靠近或远离）；`0x12` 闭锁时间（关灯后多久才能再开灯）；`0x15`/`0x16` 分距离门的运动/存在阈值可压制远端误触发 |

:::tip 一句话记住这套方案擅长什么、不擅长什么
**擅长**：近距离（吊装或侧装都能覆盖几米）、需要「静止也算有人」的场合、需要目标方位而不是纯开关量的场合。
**不擅长**：需要计量级定位、需要「绝对不漏报/不误报」、需要有责任后果的联锁（见「已知限制」）。
:::

## 2. 方案构成

```text
 ┌────────────────────┐   UART 256000 8N1  ┌──────────────────────────┐   原生 USB CDC    ┌────────────────────┐
 │  EDV163-N-03       │   大端 / 二进制帧   │  EDK60_VA V1.0           │   免驱 / 单 COM    │  Chrome / Edge     │
 │  60 GHz 人存雷达    │ ─────────────────▶ │  ESP32-C6-MINI-1-N4      │ ────────────────▶ │  presence.html     │
 │  插在 H3 插座       │ ◀───────────────── │  纯字节双向透传桥          │ ◀──────────────── │  单文件网页（唯一   │
 │                    │   SET / GET 帧      │  不解析 / 不组帧 / 不转义   │   SET 需人工确认   │  图形上位机）       │
 └────────────────────┘                     └──────────────────────────┘                   └────────────────────┘
        ▲                                              ▲
        │ 3.3V_RADAR（IO14 高有效使能）                 │ 板载 USB-C，无 USB 转串口芯片
        └──────────────────────────────────────────────┘
```

| # | 器件 / 组件 | 型号 / 规格 | 角色 | 关键点 |
|---|---|---|---|---|
| 1 | 开发板 | **EDK60_VA V1.0**（ESP32-C6-MINI-1-N4，4 MB Flash，无 PSRAM） | 桥接与供电 | 板载 USB-C，**无 USB 转串口芯片**；雷达电源受 **IO14** 控制 |
| 2 | 雷达模组 | **EDV163-N-03**（60 GHz 人存，协议 **V1.1**） | 传感 | 插 **H3**，**不要插 H4**（见 3.3） |
| 3 | 固件 | **EDV163 纯字节双向透传桥**（与水位案例同一份） | 字节搬运 | 不解析协议、不组帧、不做转义、**零日志字符**（帧尾是 `0x0A`，见 7.4） |
| 4 | 上位机 | `presence.html`（单文件网页） | 解析 + 展示 | Web Serial；默认只读；写参数逐条确认 |
| 5 | 线缆 | USB-C **数据线** | 供电 + 数据 | 纯充电线会「灯亮但电脑认不到」 |
| 6 | 安装件 | 侧装支架 / 吊装支架（可锁死角度） | 决定几何 | 姿态与挂高直接改变 `x/y/z` 的语义（见 4 节） |

| 技术点 | 选择 | 为什么 |
|---|---|---|
| 物理层 | **UART 256000 8N1，无流控，大端** | 协议《串口通信约定》明确「波特率 256000 固定」「默认大端」；**注意协议里 `0x04` 的出厂默认值是 4 = 115200，与这条约定矛盾**（7.9 b） |
| 成帧 | `45 44 \| 长度 \| msgid \| op \| type \| tlv_len \| value \| 校验和 \| 0x0A` | 长度 = `12 + N`（N 为**转义前** value 字节数）；校验和 = 自 `45` 起至 value 末字节**转义前**求和 mod 256 |
| 转义 | 正文里 `0x0A → 09 01`、`0x09 → 09 00`；**帧尾 `0x0A` 不转义** | 芯片把 `0x0A` 当帧尾，正文里出现就必须躲开（7.3） |
| 主数据源 | `0x81`（op=`A3` 主动上报，**每通道 9 B**） | 有人/无人 + 静止/运动 + 靠近/远离 + `x/y/z`（mm）一次全给（7.6） |
| 次数据源 | `0x80`（op=`A3`，**80 B**，40 门运动能量 + 40 门静止能量） | 用于距离门能量条；**是否需要先 `SET 0x1E=1` 开调试模式：待实测**（7.7） |
| 解析位置 | **全部在网页侧**，固件零协议代码 | 固件越简单，越不会污染字节流（日志换行 = 帧尾冲突） |
| 写入策略 | 默认只读；写入逐条确认、逐条等应答 | 参数写错会静默改变上报行为（如 `0x18=0` 直接关射频） |

## 3. 接线与安装

### 3.1 先认清 H3 的丝印顺序（本链路最容易搞错的一处）

板上有两个 8 pin 排针，**同一物料、同一信号集合、顺序完全相反**：

| 脚位（自上而下） | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|
| **H3**（雷达插槽，**用这个**） | RES | **A** | **R** | **T** | **G** | **V** | **P** | RES |
| **H4**（**禁止插模组**） | RES | P | V | G | T | R | A | RES |

H3 的第 1、8 脚（`RES`）在 EDV163 模组上**没有对应引脚**（模组只有 P/V/G/T/R/A 六脚），**保持空置**。

### 3.2 H3 引脚表（EDV163-N-03 ↔ EDK60）

| H3 脚 | 丝印 | 模组脚 | 板上网络 / GPIO | 信号方向 | 电平 | 本方案用不用 |
|---|---|---|---|---|---|---|
| 1 | RES | —（模组无此脚） | 复位网络（与 H4 共用） | — | — | 空置 |
| 2 | **A** | **下行通道**（模组侧收命令的那一脚，实测如此） | **IO5**（MCU 的 UART TX；发命令能收到应答） | 输入（MCU→模组） | 3.3 V | **用**（下行 SET/GET） |
| 3 | **R** | 读图上标为 UART RX，但**实测不是下行通道** | 读图对应 **IO1**，上板实测下行走的是 IO5 | — | — | **空置**（T-01 待定论） |
| 4 | **T** | **上行通道**（模组侧发数据的那一脚） | 实测 **IO4**（MCU 的 UART RX） | 输出（模组→MCU） | 3.3 V | **用**（上行帧） |
| 5 | **G** | G（GND） | GND | 共地 | 0 V | **用** |
| 6 | **V** | V（VCC 3.3 V） | `3.3V_RADAR`（LDO 输出） | 电源入 | 3.3 V DC | **用** |
| 7 | **P** | P（DC Input 3.3 V） | `3.3V_RADAR`（与 V 同网络） | 电源入 | 3.3 V DC | **用** |
| 8 | RES | —（模组无此脚） | 复位网络 | — | — | 空置 |

**串口参数**：**256000 / 8 数据位 / 无校验 / 1 停止位 / 无流控**，多字节字段**大端**。
**不需要电平转换**（模组是 3.3 V TTL，与 ESP32-C6 同电平；**也不要串电阻分压**，会破坏 256 k 波形上升沿）。

:::caution T-01：丝印命名与实测方向对不上（不影响本文接线，但插满脚前请先看）
板上**读图**把第 2 脚 `A` 当模组的 GPIO 输出、把第 3 脚 `R` 当 UART RX（→ IO1）；
但**上板实测**证明：**上行在 IO4（第 4 脚 `T`）**、**下行在 IO5（第 2 脚 `A`）**，第 3 脚那条（IO1）**根本没被用到**。

**为什么要紧**：若 `A` 真是模组的 GPIO **输出**，而它又落在 IO5（MCU 的 UART **TX 输出**）上，就是**输出对输出顶牛**。
但实测既然能用 IO5 发命令，说明模组侧这一脚**收得住数据**（功能上就是 RX）——所以本文**按实测接线**：
数据只用 `T`（IO4）与 `A`（IO5）两个信号，`R` 脚**空置不接**。

**要定论就按这三步量**：① 断电，万用表通断测 H3 第 2 脚 ↔ IO5、第 3 脚 ↔ IO1；② 只上电（EN 保持低、`3.3V_RADAR` 不输出），
把 IO5 当 GPIO 输出翻转高低，看模组/电平是否跟随；③ 结论回填到本表。**在定论之前，不要为了「用上所有脚」把 `R` 也接出去。**
:::

### 3.3 为什么必须插 H3，不要插 H4

H3 的丝印是 **`RES A R T G V P`**（两端各一个 `RES`），H4 是 **`RES P V G R T A`**——同一物料、顺序镜像。

:::warning 模组必须插 H3，不要插 H4
H4 把顺序镜像过来，`T` 与**雷达电源使能**处在同一侧的网络关系上。插 H4 **不会冒烟**，但会出现
「红灯亮着、却一个字节都没有」或者「偶发丢帧、校验大面积失败」这类最难查的现象——
因为它同时踩了两件事：**数据脚错位** + **电源与数据互相干扰**
（H4 的 `V`/`P` 不再落在 `3.3V_RADAR` 上，数据脚还可能与电源脚同网络，存在经 IO 反灌的风险）。

**插拔纪律**：**禁止在 EN = 1（雷达已上电）时插拔模组**——VCC/GND 上电顺序不可控，容易经 IO 反灌；
插拔前先让 EN = 0，确认丝印 `RADAR` 红灯灭。
:::

### 3.4 上电自检：只看一个灯

| 灯 | 丝印 | 含义 | 能不能判断雷达供电 |
|---|---|---|---|
| 绿 | `ON` | 主板 3.3 V 正常 | 不能 |
| 橙 | `L` | **普通指示灯**，与雷达电源无关 | **不能**（最容易误判的一个） |
| **红** | **`RADAR`** | 直接挂在 `3.3V_RADAR` 轨上 | **能——红灯亮 = 雷达已上电** |

**电源使能是 IO14，高有效**，且 LDO 的 EN 经电阻**下拉**到地 → **上电默认是关的**，
固件启动后主动拉高才给雷达供电（这个顺序是安全的：MCU 复位时雷达一定先掉电）。

```text
① MCU 启动（主 3.3 V + USB 枚举稳定）
② IO14 拉高 → LDO 使能 → 3.3V_RADAR 建立 → 丝印 RADAR 红灯亮
③ 模组上电复位 / 自检 / 射频校准（固件按 ≥200 ms 冗余等待）
④ 按协议 V1.1 开始上报（是否主动上报、节奏如何：待实测，见表 B ①②）
```

**失败先查**：

| 现象 | 先查什么 |
|---|---|
| 一个灯都不亮 | USB 线是不是充电线；换 USB 口（台式机优先机箱后面） |
| 绿灯亮、**红灯不亮** | 模组没插紧 / 插到了 H4 / 固件没把 IO14 拉高 |
| 红灯亮、**一个字节都没有** | 进「排障（三层）」第①层；先怀疑波特率与插错排针，**再怀疑模组固件版本** |
| 橙灯亮但红灯不亮 | 正常也可能发生，橙灯与电源无关，**不要用它判断** |

## 4. 安装几何：侧装还是吊装

### 4.1 两个口径打架，先把话说清楚

| 来源 | 说的姿态 | 关键词 |
|---|---|---|
| **站内 EDV163 模组[产品页](/modules/60GHz/edv163)** | **侧装 0.5-1.8 m**，移动/存在 **0-8 m**；应用场景写的是「卫生间、停车场占位、电话亭、投光灯、智能面板」 | 侧装、绕水平波束 |
| **人存检测的典型做法** | **吊装 2.4-3 m 俯视**，天线面朝下 | 俯视、`x/y` 平面 + `z` 高度 |
| **本协议 V1.1 的能力** | `0x25` 挂高 **1200~5000 mm**、`0x26` 检测高度、`0x27` 检测范围（`x/y` 各 ±5000 mm）、`0x81` 给 `x/y/z` 三轴 | 明确按「有挂高的俯视」设计 |

**这三条并不矛盾，但也不能混着用**：产品页的侧装口径是**电气/安装**口径（模组能这样装），
协议的 `0x25/0x26/0x27` 是**坐标与区域**口径（俯视时才有完整含义）。
所以「本项目到底侧装还是吊装」不是抄一个数字就能定的——它决定 `z` 有没有意义、`0x25` 要不要设。

### 4.2 两种姿态的取舍

| 维度 | **侧装（墙/柱，0.5-1.8 m 高）** | **吊装（天花，2.4-3 m 高，天线朝下）** |
|---|---|---|
| 波束形态 | 近似**水平**扇面，覆盖一个长条区域 | **锥形俯视**，覆盖脚下圆形区域 |
| 适合场景 | 走廊、门口侧面、卫生间外侧、投光灯/面板（贴墙安装） | 房间中央、会议室、工位上方、车位正上方 |
| `x / y` 语义 | 水平面内目标位置（左/右、远/近） | 水平面内目标位置（相对雷达投影点） |
| **`z` 语义** | **大概率无效或无意义**（目标与雷达同高，`z ≈ 0`；实测待确认） | **有意义**：目标的高度方向信息，需要挂高做参照（实测待确认，见 4.3） |
| `0x25` 挂高 | 仍需下发（协议要求，且影响内部坐标解算），但**没有物理「挂高」可量** → 填安装高度 | **必须下发**，且要用卷尺量「天线罩下沿 → 地面」 |
| `0x26` 检测高度 | 意义弱（可放开到 0~挂高） | 用来**砍掉地面杂波与天花板反射**，最有用 |
| `0x27` 检测范围 | 可用来把波束收进走廊宽度 | 可用来把房间边缘/门口挡在外面 |
| 安装难度 | 低（支架简单、走线方便） | 中（需要吊装点、要防摆、要防遮挡） |
| 典型误判风险 | 侧向多径、走过即走（穿堂）导致频繁有人/无人跳变 | 地面反射、灯盘/风口的运动干扰、安装高度不足导致近场盲区 |
| 本项目建议 | 先在**桌面/侧装**把协议跑通（最容易复现） | 跑通后再按真实场景上吊装，重标挂高 |

**结论：哪种姿态更适合你的项目，必须自己实测（表 B ⑮）——本文不替你选。**
产品页的「侧装 0.5-1.8 m」是**能这样装**，不是**只能这样装**；而一旦上吊装，`0x25` 挂高与 `z` 的语义就变成必答题。

### 4.3 吊装几何：`0x25` 挂高决定 `z` 有没有意义

```text
                 ┌──────────────┐
                 │ EDV163-N-03  │  天线面朝正下方，与地面法线夹角 ≤ ±5°
                 └──────┬───────┘
        ────────────────┴────────────────  地面（约定为 z 的参照平面）
             x  ←──────┼──────→  x         H = 挂高（SET 0x25，卷尺量「天线罩下沿 → 地面」）
                  目标：x/y 是水平位置，z ≈ 目标相对地面的高度（**待实测确认**）
```

**`z` 的两种可能，用一次实验就能分清（写进「验证清单」表 B ⑥）**：

| 假设 | 现象 | 判别法 |
|---|---|---|
| **A：`z` = 目标相对地面（0 平面）的高度** | 人站地面 → `z ≈ 0`；举高手 → `z` 变大 | 保持目标不动，只把 `SET 0x25` 从 2000 改成 3000 → **`z` 基本不变**（只是坐标解算参照变了） |
| **B：`z` = 目标相对雷达的垂直距离** | 人站地面 → `z ≈ 挂高`；举高手 → `z` 变小 | 同上改挂高 → **`z` 整体平移约 1000 mm** |

**在没做这个实验之前**，页面与自研上位机都**不要**把 `z` 拿去参与「有人/无人」判定，也不要在文档/界面里把 `z` 标注成
「身高」或「离地高度」——它现在只是一个**待定语义的第三个坐标**。

:::warning 挂高设错的后果比水位案例更隐蔽
水位案例里「挂高错 → 水位整体偏」是肉眼可见的；人存案例里挂高错，**可能只表现为 `z` 慢慢漂、或用 `0x26` 过滤时把目标滤掉**，
状态卡上的「有人/无人」看起来还是对的。所以：**首次安装必须 `GET 0x25` 回读 + 卷尺核对**，别信默认值。
:::

### 4.4 侧装几何：`x/y` 是主角，`z` 别当真

侧装（墙高 0.5-1.8 m，波束基本水平）时：

| 项 | 期望 | 判断方法 |
|---|---|---|
| `x` | 水平横向位置（左右） | 人沿墙横移，看 `x` 单调变化；反向走一次，符号应相反 |
| `y` | 水平纵向位置（远近） | 人正对雷达前后走 1 m，看 `y` 变化量是否≈1000 mm |
| `z` | 与安装高度相关的高度分量，**可能恒 0 或恒负** | 手举高/蹲下各 30 s，看 `z` 是否单调变化；**不变就说明侧装下 `z` 不可用** |
| `0x25` | 无物理挂高可量 → 填安装高度（mm） | `GET 0x25` 回读与安装高度一致，且 `0x26` 的 max 不超过挂高 |

### 4.5 安装避坑（每条都给可执行的判断方法）

| # | 现象 | 机理 | 判断方法 / 缓解 |
|---|---|---|---|
| **G-1** | 隔壁工位有人，本工位被判有人 | 60 GHz 波束有旁瓣，且反射路径会把「墙后的人」拉进来 | 用 `0x27` 把检测范围收到本工位尺寸；用 `0x29` 屏蔽区挡掉隔壁一侧；**判断法**：本工位空、隔壁有人，观察 `0x81` 的 `x/y` 是否指向隔壁（若 `x/y` 指过去，就是越界检测而不是误报） |
| **G-2** | 空房间频繁有人/无人跳变 | 灯盘、风口、窗帘、转动的风扇、晃动的绿植——都是 60 GHz 的强运动目标 | **判断法**：空房间静置 10 min，看 `0x81` 的 `motion` 是否出现 2（运动）；出现就逐个关灯/停风定位 |
| **G-3** | 吊装高度不够，正下方盲区大 | 近距离近场区未标注（**待实测**） | **判断法**：人站正下方看 `presence` 是否为 0；抬高安装或把 `0x26` 下限放开，再复测 |
| **G-4** | 隔玻璃/亚克力罩后检测变差 | 介质损耗与多次反射 | **判断法**：加罩/去罩各采 5 min，比 `presence` 为 1 的帧占比；用低损耗塑料（ABS/PP/PE）薄罩，**别用金属罩正对波束** |
| **G-5** | 人走了灯不灭 / 人还在灯灭了 | `0x11` 检测延时 + 上报节奏 + `0x1D` 30 min 规则的组合效应 | **判断法**：秒表测「离开 → 状态变 0」的时长，与 `0x11` 设定值比对（表 B ⑦）；把 `0x1D` 关掉再看是否还发生 |
| **G-6** | 支架轻微松动后 `x/y` 整体偏移 | 坐标原点绑定在雷达姿态上 | **判断法**：固定目标、连续 10 min 看同一位置的 `x/y` 均值是否漂移；漂了先查机械，再查标定 |

## 5. 两条烧录路径

固件名（本案例）：**EDV163 纯字节双向透传桥**。它的全部工作就是：把 **IO4** 收到的字节**原样**写到 USB，

## 6. 网页人存演示页

**[🧍 网页人体存在演示（EDV163-N-03）](pathname:///edk60/edv163-presence/presence.html)**

- 单文件 HTML，用 Chrome / Edge 打开即可，**不用装任何软件**；
- 也可以另存为本地 `presence.html`，在保存目录起静态服务（`py -3 -m http.server 8771`），访问 `http://127.0.0.1:8771/presence.html`；
- 整个页面**无外链**、不写 localStorage / IndexedDB / Cookie，刷新即清空。

### 6.1 它是「默认只读」的（本项目的一条硬约束）

| 行为 | 说明 |
|---|---|
| 连接后自动发的帧 | **只有 `op=0xA0`（GET），共 14 条**：100 ms 起重置、每 60 ms 一条，**按固定时序连发 14 条（不逐条等应答）**。顺序是 `0x02` 模块信息 → `0x11` 检测延时 → `0x12` 闭锁 → `0x17` 上报频率 → `0x18` 工作模式 → `0x1B` 触发使能 → `0x1C` 无人后持续存在 → `0x1D` 30 min 强制无人 → `0x1E` 调试模式 → `0x24` 触发模式 → `0x25` 挂高 → `0x13` 通道数 → `0x14` 通道范围 → `0x27` 检测范围 |
| 会不会改你的设备配置 | **不会**。「参数回读（默认只读）」面板里的数值只来自设备真实应答（没应答就显示 `—`，**不填默认值**） |
| 什么时候才会写 | 只有两个入口：①「**应用演示推荐参数…（需确认）**」——一个总确认框列出 5 条 SET 的改动，确认后逐条下发；②「**恢复出厂设置 0x1F…（双重确认）**」——先勾「我已知晓」解锁，再过两道确认框（第二道要求手动输入 `1F`） |
| 逐条纪律 | 逐条下发、逐条等应答（`0xA2` 应答或 `0xA9` ACK **都算已应答，不解释 ACK 载荷**），**单条 500 ms 超时即中止**、后续一条都不发；每条 SET 之后**立即回读同 type 并比对** |
| 取消确认框 | **一帧都不发**（解锁勾选本身也不发帧） |
| 兜底监控 | 确认流程之外若出现 `op=0xA1`，日志会打一行「内部告警：在未确认的写入流程之外发出了 SET（不应发生，请报告）」 |

> ⚠️ **同一时刻只能有一个程序占用这个 COM 口**：网页与命令行工具（串口助手、自研脚本）同时开会互相抢端口，
> 表现为两边都时断时续——这种「数据看起来像丢了」的现象，90% 是端口争用，不是雷达问题。

### 6.2 四块 UI

| 区块 | 显示什么 | 数据来源 | 读的时候注意什么 |
|---|---|---|---|
| **① 有人/无人状态卡** | 大字「有人 / 无人 / 无人（按静默推断）/ 等待数据」；副行给 `静止 / 运动 / 靠近 / 远离`；旁边两个 chip：**判定依据**（真帧 / 超时推断（静默 X s）/ 无帧）与**静默窗** `max(3×周期, 8 s)` | `0x81` 第 1、2、3 字节 + 到达时刻 | 「无人（按静默推断）」不是设备说的，是**超时推的**（6.4）；判定依据为「超时推断」时先确认链路没断 |

| **④ 事件时间线** | 一行一条：时刻 + 事件（`有人` / `无人` / `静止→运动` / `靠近` / `远离` / 坏帧 / 转义错误） | 解析器状态机 | 只保留最近 N 条在内存；**刷新即清空**，页面不提供导出——要留证据就在「原始帧日志」里逐行抄 |

### 6.3 统计条各项含义

| 统计项 | 含义 | 正常值 | 异常判据 / 怎么用 |
|---|---|---|---|
| 串口 | 当前设备与连接状态 | 显示你的 `COMx`、已连接 | 显示「未连接」→ 先连接（排障第①层） |
| 总字节 | 本次连接累计收到的字节数 | 持续增长 | 停滞 → 链路断了或模组没上电 |
| 帧数 | 通过校验的帧总数 | 持续增长 | 与 `0x81 + 0x80` 差很多 → 混了别的 type |
| `0x81` | 有人状态上报帧计数 | 有人时持续增长 | 恒 0 但总字节在涨 → 帧同步/长度口径问题（7.1、7.5） |
| `0x80` | 能量帧计数 | 可能恒 0（待实测） | 恒 0 且你要用能量条 → 试 `SET 0x1E=1`（7.7） |
| 坏帧（+率） | **长度非法 / 校验和错 / 帧尾异常 / TLV 长度非法 / 载荷口径异常 / 截断 / 转义非法**；实现里 `badFrames` 是这 7 类的合计（后四类分别对应 `badTlv` / `badPayload` / `truncated` / `badEscape`），**「坏帧率」的分子就是这些之和** | 0（或极低） | 持续增长 → 转义或长度口径错，或流里混了日志文本（7.4） |
| 未归属（+率） | 既不在帧内、也不是合法帧头的字节 | 0 | 增长 → 假同步或流污染 |
| **转义错误** | `09` 后面跟的不是 `00` / `01` | **0** | 增长 → 先修转义再谈其他（7.3） |
| **口径歧义** | 同一候选帧用「未转义」「已转义」两种口径都能过校验（或都不能），无法裁定 | **0** | 增长 → 流里有歧义字节（噪声/坏帧/波特率临界）；先查线材与 USB 口 |
| 帧间隔 | 相邻两帧的到达间隔 | 有人时 ≈ `0x17` × 100 ms | 忽大忽小 → USB 侧背压或设备节流；恒 `—` → 还没收到两帧 |
| 判定依据 | 状态卡这次「有人/无人」的来源 | 有人时 = 真帧 | 长期「超时推断」→ 设备静默（可能正常）；「无帧」→ 从没收到 `0x81`（排障第②层） |

### 6.4 「无人（按静默推断）」的口径

协议对 `0x17` 的原文是：**「雷达触发有人后，每隔所设置的时间上报一次有无人状态」**。这句话有个要命的推论：

| 事实 | 后果 |
|---|---|
| 上报是**「触发有人后」**才开始的 | 房间一直没人时，可能**一条 `0x81` 都不来** |
| 无人状态的帧**是否发送、发几次，原文没写死** | 所以**不能**写「等到 `presence=0` 的帧才算无人」——你可能永远等不到 |
| `0x17` 出厂默认 **50（×100 ms = 5 s）** | 就算有人，5 s 一帧也意味着「离开后 5 s 内界面还显示有人」是**正常**的 |
| `0x24` 出厂默认 **0（正常运动触发）** + 上报是「触发有人后」才开始的 | **有人但完全静止、又没有新的运动触发**时，上报也可能停掉 → 界面按静默推断显示「无人」，**把本方案的核心卖点显示成反面，而且不报故障**（见下方「静默的两种原因」，待实测表 B ②-b） |

**页面采用这个口径（术语与页内 chip 一致）**：

```text
静默窗 T = max(3 × 上报周期, 8 s)     # 上报周期 = 0x17 × 100 ms；0x17 还没回读到就按出厂 50（5 s）算 → T = 15 s
窗内收到 0x81   → 判定依据 = 真帧，presence 取帧内值（有人 / 无人）
超窗静默        → 显示「无人（按静默推断）」，判定依据 = 超时推断（静默 X s），**协议允许，不是故障**
从未收到 0x81   → 判定依据 = 无帧，显示「等待数据」
```

| 显示 | 判定依据 | 含义 | 你该做什么 |
|---|---|---|---|
| 「有人」 | 真帧（有人） | 窗内最后一条 `0x81` 说 `presence=1` | — |
| 「无人（设备判定）」 | 真帧（无人） | 窗内最后一条 `0x81` 说 `presence=0` | — |
| 「无人（按静默推断）」 | 超时推断（静默 X s） | 已超窗，**设备没说话** | 先确认是「无人所以静默」还是「链路断了」：看总字节是否还在涨、红灯是否还亮；**同时不得据此断言无人**——也可能是「有人但静止」（见下方「静默的两种原因」） |
| 「等待数据」 | 无帧 | 本次连接还没收到过 `0x81` | 排障第②层 |

**静默有两种原因——「无人（按静默推断）」不能断言无人**：

| 静默原因 | 为什么会静默 | 界面处置 |
|---|---|---|
| **真无人** | `0x17` 原文「雷达**触发有人后**，每隔所设置的时间上报一次」——没人触发过，本来就可以一条都不发 | 显示「无人（按静默推断）」可以接受，但必须标明是推断值、不是设备判定 |
| **有人但完全静止、未触发上报** | `0x24` 出厂默认 **0 = 正常运动触发**；先被运动触发过才开始按 `0x17` 上报，一旦静止超过 `0x11` 保持窗（默认 10 s）、又没有新的运动触发，上报可能停掉 | **静默推断时不得断言无人**：状态卡要给出「静默 X s」与最后一条帧的时间，并提示「**若刚有运动触发过，勿据此判无人**」；末帧的 `presence` 原值以「原始帧日志」为准（状态卡大字在静默时固定显示「无人（按静默推断）」，不声称是设备判定） |

> ⚠️ **这条待实测**（表 B ②-b）：让一个人坐着不动 10 min，看相邻帧间隔会不会同样拉长。
> 若会，则「静默 = 无人」在静坐场景**直接反了**——这是本方案最容易被自己的界面骗过去的失败模式：
> 人明明还在，界面却显示「无人」，而且**不报任何故障**。

:::danger 自研上位机最容易犯的错
**只等 `presence=0` 的帧** → 房间空下来以后界面**永远显示「有人」**，而且没有任何报错。
正确做法是「**最后一条帧 + 超时**」两个信息一起用，并且把「静默秒数」显示出来——让人一眼看出这是推断值，不是设备值。
:::

## 7. 协议逐字节拆解

这一节够你从零写出自己的上位机。**固件一行协议代码都没有**——帧头、长度、校验和、转义、`0x81` 通道切分、
静默推断、参数回读，全部在上位机侧。

### 7.1 帧结构与组帧规则

```text
 0        2        4        6    7    8        10            N+10      N+11
+--------+--------+--------+----+----+--------+------------+---------+--------+
|45 44   | 长度   | msgid  | op |type|tlv_len |  数据区 N  | 校验和  | 0x0A   |
| 2B     | 2B BE  | 2B BE  |1B  |1B  | 2B BE  |  N B       |   1B    | 帧尾   |
+--------+--------+--------+----+----+--------+------------+---------+--------+
长度 = 12 + N（N = value 的【转义前】字节数；整帧含帧尾，所以 N=0 的 GET 帧是 12 B）
校验和 = Σ(0x45 .. value 末字节) mod 256  —— 一律按【转义前】算
组包顺序：算长度/校验和 → 追加校验和 → 对「帧头..校验和」整段转义 → 最后追加帧尾 0x0A
解包顺序：边收边还原转义 → 按【声明长度】切帧 → 验校验和 → 取 value → 按 type 解字段
```

| 字段 | 偏移 | 长度 | 编码 | 说明 |
|---|---|---|---|---|
| 帧头 | 0 | 2 | `0x45 0x44` | 固定（ASCII `"ED"`） |
| 长度 | 2 | 2 | uint16 **大端** | **`12 + N`**，N 为**转义前** value 字节数；含帧尾 |
| msg id | 4 | 2 | uint16 大端 | 传输序列号，范围 0~0xFFF0，到顶回 0；应答回显请求的 id |
| op | 6 | 1 | uint8 | 见 7.2 |
| type | 7 | 1 | uint8 | 见 7.2 与「参数配置」 |
| TLV 长度 | 8 | 2 | uint16 大端 | 必须 = 长度 − 12 = N（**转义前**） |
| 数据区 | 10 | N | 视 type | value；**可连续多个 `type+length+value`**（本文只用单 TLV） |
| 校验和 | 10+N | 1 | uint8 | `Σ(0x45 .. 数据区末) mod 256`，**转义前** |
| 帧尾 | 11+N | 1 | `0x0A` | **固定，永不转义** |

**组帧伪代码**（本文所有帧就是这段逻辑跑出来的，你可以照抄核对）：

```python
def build_frame(op, typ, value=b"", msgid=1):
    n = len(value)
    total = 12 + n                       # 声明长度：含帧头…帧尾，按【转义前】算
    body = bytes([0x45, 0x44, total >> 8, total & 0xFF,
                  msgid >> 8, msgid & 0xFF, op, typ,
                  n >> 8, n & 0xFF]) + value
    cs = sum(body) & 0xFF                # 自 0x45 起，到 value 末字节
    wire = bytearray()
    for b in body + bytes([cs]):         # 只转义「帧头…校验和」
        if b == 0x0A:  wire += b"\x09\x01"
        elif b == 0x09: wire += b"\x09\x00"
        else:           wire.append(b)
    wire.append(0x0A)                    # 帧尾最后追加，永不转义
    return bytes(wire)
```

**校验和算例（脚本算的，禁止手算）**：

```text
① GET 0x02（读模块信息，N=0）—— 只列到 value 末字节（本帧没有 value），校验和与帧尾在下一步追加
   45 44 00 0C 00 01 A0 02 00 00
   = 69 + 68 + 0 + 12 + 0 + 1 + 160 + 2 + 0 + 0 = 312
   312 mod 256 = 56 = 0x38                        ✅ 校验和 = 0x38

② SET 0x17 = 10（上报周期 1 s，N=2；value = 00 0A）—— 同样只列到 value 末字节（注意这个 0x0A 不是帧尾！）
   45 44 00 0E 00 01 A1 17 00 02 00 0A
   = 69 + 68 + 0 + 14 + 0 + 1 + 161 + 23 + 0 + 2 + 0 + 10 = 348
   348 mod 256 = 92 = 0x5C                        ✅ 校验和 = 0x5C
   注意：校验和按【转义前】算，与线上字节数无关（这条帧线上 15 B、声明 14 B，见 7.5）
```

:::danger 三条组帧纪律（每条都有真实事故原型）
1. **永远用程序组帧**：不要手抄别人的 hex、不要心算校验和。本项目历史上出现过「手算校验和差 4，导致 GET 完全无应答」。
2. **先转义、最后贴帧尾**：反过来（先贴帧尾再整段转义）会把帧尾转义成 `09 01`，设备**永远等不到帧尾**。
3. **发送前把声明长度、线上字节数、校验和三样打印出来对一眼**：三者互相对不上，就是转义或长度口径错了。
:::

### 7.2 op 与 type 速查

| op | 含义 | 谁发 | 本方案怎么用 |
|---|---|---|---|
| `0xA0` | Get（参数获取） | 上位机 | 连接后只读体检；写之前先回读 |
| `0xA1` | Set（参数设置） | 上位机 | 只在确认框之后发 |
| `0xA2` | Report（对 Get/Set 的**被动**应答） | 雷达 | 逐条等它，超时即停 |
| `0xA3` | Status（**主动**上报） | 雷达 | `0x81` / `0x80` 走这条 |
| `0xA4` | 透传（**预留**） | — | 本版不用 |
| `0xA9` | ACK | 雷达 | `0xA9` ACK 仅表示「设备收到了」，**协议未定义其载荷长度与状态码**（原文只写「ack回复」）；因此**收到即视为已应答，不解释载荷**，成功判定以 `0xA2` 应答 + 回读比对为准 |

**type 分区**（细节与默认值见「参数配置」节；这里只给你一张地图）：

| 分区 | type | 说明 |
|---|---|---|
| 标识信息 | `0x01` 产品信息（3 B）、`0x02` 雷达模块信息（16 B） | 只读；**`0x02` 的出厂默认串不是本型号，见 8.1 陷阱 ①** |
| 通信与节奏 | `0x04` 波特率（1 B 枚举）、`0x17` 状态上报频率（2 B，单位 100 ms） | `0x04` 改动会**立即改变设备波特率**，高危 |
| 检测逻辑 | `0x11` 检测延时、`0x12` 闭锁、`0x13` 通道数、`0x14` 通道范围、`0x15` 运动阈值、`0x16` 存在阈值、`0x1B` 触发使能、`0x1C` 无人后持续存在检测、`0x1D` 30 min 强制无人 | 人存「状态不对」几乎都出在这一组 |
| 开关与调试 | `0x18` 工作模式、`0x19` 雷达频率、`0x1A` 强制进入无人、`0x1E` 调试模式、`0x1F` 出厂设置 | `0x18=0` 关射频、`0x1F=1` 恢复出厂，两条都能把演示搞崩 |

### 7.3 转义规则与三条连锁后果

| 方向 | 规则 |
|---|---|
| 发送（转义） | 正文 `0x0A → 0x09 0x01`、`0x09 → 0x09 0x00`；**帧尾 `0x0A` 不在正文里，不转义** |
| 接收（还原） | `09 01 → 0x0A`、`09 00 → 0x09`；`0x09` 后跟其它字节 = **非法转义** |
| 作用范围 | 帧头 … 校验和（共 `长度-1` 字节）；帧尾在转义**之后**追加 |
| 长度 / 校验和 | 一律按**转义前**（= 还原后）的字节序列计算，**与线上字节数无关** |

**接收侧正确的处理顺序**（顺序错一步就全错）：**边收边还原 → 按声明长度切帧 → 验校验和 → 解 value**。

**怎么区分「转义序列 `09 01`」和「真帧尾 `0x0A`」**（接收侧唯一的技巧）：

- 逐「线上」字节推进，同时累积还原后的缓冲；
- **只有当前字节是 `0x0A` 且它前面没有 `0x09` 引导时，才是真帧尾**；
- `0x09` 后面的字节一定是 `00` / `01`（否则判非法转义，**只 skip 1 字节**重同步，不要整段 flush）；
- 任何非法形态都只丢 1 个字节——这样截断帧、坏校验和、非法转义之后都能重新捕获下一条好帧。

**三条连锁后果（这是本协议最容易「静默错」的地方）**：

| # | 后果 | 具体表现 | 处置 |
|---|---|---|---|
| 1 | **声明长度 ≠ 线上字节数** | 声明 14 B 的 `SET 0x17=10` 在线上是 15 B；如果按线上字节数切帧，一旦 value 里有 `0x09`/`0x0A` 就整体错位 | 切帧一律用**声明长度**（转义前）；「线上字节数」只用来做统计与告警 |
| 2 | **`0x0A` 既是帧尾、也可能在正文里** | 直接按 `0x0A` 找帧尾，会在正文里的 `0x0A` 处**提前截断**——这一帧丢掉，且后面的字节要重同步 | 先还原再切帧；坏帧计数会告诉你这件事正在发生 |
| 3 | **任何 printf 日志的换行都会切断帧** | 固件打一行日志 = 往流里插一个 `0x0A`，接收侧就把当前帧截断；更糟的是 `"EDK60"` 前两字节正好是 `0x45 0x44`（假帧头） | 固件**零日志字符**（7.4）；不要用串口助手文本模式判断链路好坏 |

:::caution 协议原文对转义的说明只写了一半（矛盾 c，见 7.9）
原文：「芯片通信会识别 `0x0A` 为帧尾，其它地方出现 `0x0A` 时需要做转义处理……**只用在发送给模块数据的最后面做处理**，其它地方都不用变」。
这句只明确了**主机 → 模组的发送方向**，**没说模组 → 主机的上报帧是否也转义**。

**工程处置（双口径，两种设备行为都安全）**：接收侧对每个候选帧**两种口径都试**——
口径 A「未转义」（线上字节即还原后字节）、口径 B「已转义」（先把 `09 01` / `09 00` 还原再按长度切），
**取校验和通过的那一个**；两种都能过（或都不能）时计入「口径歧义」（正常应恒 0）。
这比「只按一种口径还原」更稳：设备不转义而正文里恰好有裸 `0x0A` 时，口径 A 仍能救回这一帧。

**取证方式**：看「原始帧日志」里每帧末尾的「N 处转义」标注——**单通道 `0x81` 帧至少 1 处**
（`tlv_len = 9 = 0x0009`，低字节 `0x09` 必须转义成 `09 00`，见 7.5 的合成帧），常见 2~3 处。
「转义对计数恒为 0」只可能是两种情况：切帧口径错，或设备真不转义——**两种都要在验收记录里点名**。
（同理：若日志里一帧都看不到「N 处转义」标注，也要按这两条查。）
:::

### 7.4 为什么固件必须零日志（这不是洁癖，是功能前提）

帧尾是 `0x0A`，而文本日志的换行也是 `0x0A` → 一行日志**直接把当前帧切断**；
更阴的是项目名 `EDK60` 的前两字节正好是 `0x45 0x44`，任何含它的日志/横幅都会造出**假帧头**，接收侧跟着假同步。
所以「静默」要四道保险 + 一道门禁：日志级别编译期消失、启动横幅/引脚表关闭、源码零 `printf`、
运行期 `esp_log_level_set("*", ESP_LOG_NONE)`，再加编译期分派表里整块跳过横幅。
若上板后仍看到 `I (115) esp_image: …`，那是 **bootloader 阶段日志**——它不受应用日志级别管，要单独把 bootloader 日志级别设为 NONE。

### 7.5 完整帧逐字节样例（7 条主机帧 + 1 条应答 + 2 条合成上报）

> **本表字节、校验和、转义后的线上字节全部由脚本生成并逐字节复核**（逻辑即 7.1 伪代码，`msgid = 0x0001`）。
> 它们**不是设备抓包**；发送前仍建议用你自己的脚本现算一遍。表中「转义」列写的是**转义处数与位置**。

| # | 用途 | op | type | value（转义前） | 声明长度 | **线上字节** | 校验和 | 转义 |
|---|---|---|---|---|---|---|---|---|
| 1 | 读模块信息（`GET 0x02`） | `A0` | `02` | —（N=0） | 12 | **12 B** | `0x38` | 无 |
| 2 | 回读上报频率（`GET 0x17`） | `A0` | `17` | —（N=0） | 12 | **12 B** | `0x4D` | 无 |
| 3 | **上报周期 = 1 s（`SET 0x17=10`）** | `A1` | `17` | `00 0A` | 14 | **15 B** | `0x5C` | **1 处**（value 低字节 `0x0A → 09 01`） |
| 4 | 检测延时 = 3 s（`SET 0x11=3`） | `A1` | `11` | `00 03` | 14 | **14 B** | `0x4F` | 无 |
| 5 | 触发模式 = 0（`SET 0x24=0`） | `A1` | `24` | `00` | 13 | **13 B** | `0x5D` | 无 |
| 6 | **挂高 = 2500 mm（`SET 0x25=2500`）** | `A1` | `25` | `09 C4` | 14 | **15 B** | `0x2D` | **1 处**（value 高字节 `0x09 → 09 00`） |
| 7 | 调试模式 = 1（`SET 0x1E=1`） | `A1` | `1E` | `01` | 13 | **13 B** | `0x58` | 无 |

**逐条线上字节（照抄可用，含帧尾）**：

```text
① GET 0x02     45 44 00 0C 00 01 A0 02 00 00 38 0A                          (12 B)
② GET 0x17     45 44 00 0C 00 01 A0 17 00 00 4D 0A                          (12 B)
③ SET 0x17=10  45 44 00 0E 00 01 A1 17 00 02 00 09 01 5C 0A                 (15 B，声明 14)
④ SET 0x11=3   45 44 00 0E 00 01 A1 11 00 02 00 03 4F 0A                    (14 B)
⑤ SET 0x24=0   45 44 00 0D 00 01 A1 24 00 01 00 5D 0A                       (13 B)
⑥ SET 0x25=2500 45 44 00 0E 00 01 A1 25 00 02 09 00 C4 2D 0A                (15 B，声明 14)
⑦ SET 0x1E=1   45 44 00 0D 00 01 A1 1E 00 01 01 58 0A                       (13 B)
```

**两条容易被忽略的旁证（同一份脚本产出）**：

| 情形 | 声明长度 | 线上字节 | 校验和 | 说明 |
|---|---|---|---|---|
| 设备应答 `GET 0x17`（假设回 `00 0A`，即 1 s） | 14 | **15 B** | `0x5D` | `45 44 00 0E 00 01 A2 17 00 02 00 09 01 5D 0A` —— **应答方向同样需要转义还原** |
| `SET 0x1F=1`（恢复出厂，**高危**） | 13 | 13 B | `0x59` | `45 44 00 0D 00 01 A1 1F 00 01 01 59 0A` —— 一帧就把设备打回默认（含 `0x17=50`、`0x1E=0`） |

:::warning 关于 `SET 0x17` 这一帧，协议原文自己有一处口径偏差
原文示例「设置状态上报频率为1s」写的是：`45 44 00 0D 00 01 A1 17 00 01 09 01 5A 0A`
—— 它把 value 当成 **1 字节**（`tlv_len = 0x0001`、声明长度 `0x0D = 13`）。
但同一份协议的类型表里，`0x17` 明确是 **2 Byte** 字段（单位 100 ms）。

**本文按类型表实现（2 字节，`tlv_len = 2`、声明长度 14、线上 15）**，理由是：
① 类型表是权威字段定义；② 取值范围 1~65535（默认 50）本来就不是 1 字节装得下的量。
**这条差异已列入待实测**（表 B ⑩）：真机若只接受 1 字节形式，`GET 0x17` 的回读长度会立刻暴露（回 1 B 还是 2 B）。
:::

### 7.6 `0x81` 上报载荷：**每通道 9 字节**（与站内旧口径 7 B 的正面冲突）

```text
value = N × 9 字节（N = 通道数，由 0x13 设定，1~4）
        每通道 9 B：
        [0] 有人/无人        0 无人 / 1 有人
        [1] 无人/静止/运动    0 无人 / 1 静止 / 2 运动
        [2] 静止/靠近/远离    0 静止 / 1 靠近 / 2 远离
        [3:5] x   int16 大端，mm（有符号）
        [5:7] y   int16 大端，mm（有符号）
        [7:9] z   int16 大端，mm（有符号）
tlv_len 必须 = 9 × N，否则判「载荷口径异常」——绝不按 7 或 8 去猜
```

| 偏移（通道首字节起） | 长度 | 字段 | 类型 | 说明 |
|---|---|---|---|---|
| 0 | 1 | `presence` | uint8 | 0 无人 / 1 有人（**带「通道延时有无人状态」语义，即受 `0x11` 延时影响**——原文此句本身残缺，属**推断，待实测**） |
| 1 | 1 | `motion` | uint8 | 0 无人 / 1 静止 / 2 运动 |
| 2 | 1 | `direction` | uint8 | 0 静止 / 1 靠近 / 2 远离（受 `0x24` 触发模式影响） |
| 3 | 2 | `x` | **int16 大端** | mm，**有符号**（负值合法） |
| 5 | 2 | `y` | **int16 大端** | mm，有符号 |
| 7 | 2 | `z` | **int16 大端** | mm，有符号；语义待实测（4.3） |

**通道数怎么定**：`0x13`（1~4）决定通道数，帧内**按通道顺序**连着排 9 B × N。
协议原文对 `0x81` 只列了 9 个字段、**没有 count 前缀、也没有通道序号字节**——
所以「通道顺序 ↔ 物理位置」的对应关系**只能靠实测**（表 B ④⑤）。
若你收到的 `tlv_len` 是 `1 + 9N`（多一个字节）或 `1 + 7N`（旧口径），**不要凑合解**，先判口径异常并取证。

#### 与站内旧口径（水位指南的 7 B/通道）并排对比

| 项 | **本文口径（协议 V1.1，9 B/通道）** | 站内水位指南口径（旧，7 B/通道） |
|---|---|---|
| 载荷开头 | **直接就是第 1 通道的第 1 个字段**（无 count 前缀） | **1 B 通道数 count**，然后逐通道 |
| 每通道字段 | `presence / motion / direction / x(i16) / y(i16) / z(i16)` = **9 B** | `channel / delay_presence / target_state / motion_direction / distance(u16) / angle(i8)` = **7 B** |
| 通道号在哪 | **不在载荷里**（顺序即通道号） | 每通道第 1 字节 `channel` |
| 坐标 | **三维 `x/y/z`（int16，mm）** | 只有 `target_distance`(u16) + `target_angle`(int8)，**没有三维坐标** |
| `tlv_len` 公式 | `9 × N` → 9 / 18 / 27 / 36 | `1 + 7 × N` → 8 / 15 / 22 / 29 |
| 适用模组/文档 | EDV163-N-03，《EDV163 替换 EDQ152 成品通用协议 V1.1》 | EDV163（水位/测距），另一份协议 + 驱动源码 |

#### 错位演示：同一条 18 B 载荷，两种口径解出什么（合成帧自测，非设备实测）

载荷（脚本构造，2 通道）：`01 02 01 04 D2 FD D0 08 34 01 01 00 FF 9C 00 FA 05 78`

| 解析口径 | 结果 |
|---|---|
| **按 9 B/通道（本文）** | `tlv_len = 18` → **2 个通道**。通道1：有人 / 运动 / 靠近，`x = +1234`、`y = −560`、`z = +2100`；通道2：有人 / 静止 / 静止，`x = −100`、`y = +250`、`z = +1400` |
| 按 7 B/通道（旧口径） | 首字节当 count → `count = 1`；通道1 解出 `channel = 2`、`delay_presence = 1`、**`target_state = 4`（枚举里没有 4）**、`motion = 210`、`distance = 64976 mm`、`angle = 8`；**还剩 10 字节没被消费**（18 − 1 − 7×1） |

**这就是「一眼看出口径错」的判据**：`target_state = 4`、`motion = 210`、`distance = 64976` 这类值**在枚举/量程里根本不存在**。
而**单通道**的时候，旧口径会「读 7 字节、剩 1 字节不消费」，很多实现直接忽略剩字节 → **恰好不报错**，
于是这个 bug 会一直潜伏到**第 2 个通道出现**才爆发。所以：

:::danger 判据（照做，不要猜）
① `tlv_len % 9 == 0` 才继续，否则把整帧记为「**载荷口径异常**」并在日志里打印原始 `tlv_len` 与 value 十六进制；
② `通道数 = tlv_len ÷ 9`，范围必须 1~4，超出即异常（`0x13` 只允许 1~4）；
③ 每通道三个枚举字节必须分别落在 0/1、0/1/2、0/1/2 三组取值内，出现 3 以上即判异常；
④ **绝不允许**「`tlv_len` 除不尽就按 8 或 7 反推通道数」——猜错就是静默渲染垃圾数据。
:::

#### 两条由脚本证明的「必踩点」

| # | 事实 | 证据（脚本输出） |
|---|---|---|
| 1 | **单通道 `0x81` 帧必然含 1 处转义** | `tlv_len = 9 = 0x0009`，低字节就是 `0x09` → 必须转义成 `09 00`。合成帧线上字节：`45 44 00 15 00 01 A3 81 00 09 00 01 02 01 04 D2 FD D0 08 34 AF 0A`（声明 21 B / 线上 **22 B**，校验和 `0xAF`） |
| 2 | 双通道帧可能**不含**转义 | `tlv_len = 18 = 0x0012`，无 `0x09`/`0x0A`；合成帧：`45 44 00 1E 00 01 A3 81 00 12 01 02 01 04 D2 FD D0 08 34 01 01 00 FF 9C 00 FA 05 78 D5 0A`（声明 30 B / 线上 **30 B**，校验和 `0xD5`） |

> **所以「转义对还原数 > 0」是一条硬判据**：只要你收到过任意一帧单通道 `0x81`，就必然至少还原过 1 个 `09 00`。
> 若该计数恒为 0 而 `0x81` 帧数在涨，说明你的切帧/还原顺序错了（先切后还原、或根本没还原）。

### 7.7 `0x80` 能量帧与调试模式（**整节待实测**）

| 项 | 协议原文 | 本文口径 / 待实测点 |
|---|---|---|
| type | `0x80`「调试数据输出」 | op 为 `A3`（status） |
| 长度 | **80 Byte** | 固定 80 B：**1-40 B = 40 个距离门的运动能量**，**41-80 B = 40 个距离门的静止能量**，取值 **0-100** |
| 允许操作 | `status` | **不能 GET**（原文没给 Get/Set） |
| 触发条件 | 原文未写 | ⚠️ **推断需先 `SET 0x1E=1` 打开调试模式才有输出** —— 这条**没有原文依据，是待实测项**（表 B ③） |

**为什么值得试**：40 个距离门的能量条能让你**看见目标在哪个距离门**，用来判断「人在 2 m 还是 4 m」「是不是墙在动」。
**为什么不能依赖它**：它叫「调试数据」，很可能是低优先级/仅调试期输出；一旦设备固件关掉这个通道，你的能量条就空了。

**若拿不到 `0x80`，四步降级（页面已按这个顺序提示）**：

| 降级档 | 做法 | 代价 |
|---|---|---|
| ① 先确认前提 | `GET 0x1E` 回读是否 = 1；没有就（在确认框后）`SET 0x1E=1`；再采 5 min 看 `0x80` 帧数是否 &gt; 0 | 若 5 min 仍是 0 → 判定「该固件不输出 `0x80`」并记入验收记录 |
| ② 用 `0x81` 顶上 | 状态卡 + `x/y` 散点 + 事件时间线全部可用，**只丢能量条** | 失去「距离门分辨」，只有目标坐标 |
| ③ 用区域代替距离门 | 把 `0x27` 检测范围收到你要的区域，**范围本身就是筛子**；配合 `0x15`/`0x16` 阈值与 `0x29` 屏蔽区 | 不能量化能量，只能做「在区内/区外」 |
| ④ 自研兜底 | 用 `0x81` 的 `x/y` 累积散点密度图（同一批帧的落点分布）近似「人常在哪」 | 是统计图，不是瞬时能量；且需要自己落盘 |

### 7.8 主机 → 模组 50 B 上限的推论（屏蔽区分批）

协议原文：「**雷达接收数据最长为 50BYTE，超过 50BYTE 的部分不会识别**」——说的是**主机发给模组**的帧。

```text
整帧（转义前）= 12 + N ≤ 50   ⇒   N ≤ 38
（协议未说明 50 B 是按转义前还是转义后计；本文按转义前算，并在选型时给转义留余量）
（演示页取更保守口径：转义前 12 + N ≤ 50 【且】转义后线上字节数 ≤ 50，两道闸都过才发；
  于是「2 块屏蔽区」在页面里是硬拒而不是软警告——两处口径不冲突，页面只是更严）
```

| type | value 结构 | N | 整帧（转义前） | 是否超 50 B |
|---|---|---|---|---|
| `0x26` 检测高度 | 4 B（min/max 各 u16） | 4 | 16 | 否 |
| `0x14` 通道范围 | 13 B（1 + 4 个 u16 距离 + 4 个 int8 角度） | 13 | 25 | 否 |
| `0x27` 检测范围 | 16 B（8 × i16） | 16 | 28 | 否 |
| **`0x29` 屏蔽区 × 1** | 1 + 13×1 | 14 | 26 | 否 |
| **`0x29` 屏蔽区 × 2** | 1 + 13×2 | 27 | **39** | 否（本文推荐上限） |
| **`0x29` 屏蔽区 × 3** | 1 + 13×3 | 40 | **52** | **是——超限，设备会截断/不识别** |
| `0x81` 上报（反向，不受此限） | 9 × N | 9/18/27/36 | 21/30/39/48 | 否（4 通道仍 48 B） |

:::warning 这条「每帧最多 2 块屏蔽区」是**推论**，不是原文条款
协议只允许配 **0~10 个**屏蔽区，却没有给「怎么分批下发」的说明。本文的推论是：
**50 B 上限 ÷ 每块 13 B → 一帧最多塞 2 块**（3 块 = 52 B 必超）。
**待实机确认三件事**：① 50 B 是按转义前还是转义后算；② 分 5 帧下发 10 块，后面的帧会不会**覆盖**前面的（而不是追加）；
③ `GET 0x29` 时 value 怎么填（原文只对 `0x15`/`0x16` 明说「get 时需要补 0」，`0x29` 没写）。
在确认之前：**屏蔽区最多下发 2 块**，多出来的用 `0x27` 检测范围去挡。
:::

**可复制的 2 块屏蔽区帧**（脚本生成，示例坐标：X ±500 mm、Y 0~500 mm、Z 0~2000 mm，两块相同）：
`45 44 00 27 00 01 A1 29 00 1B 02 01 FE 0C 01 F4 00 00 01 F4 00 00 07 D0 02 FE 0C 01 F4 00 00 01 F4 00 00 07 D0 31 0A`
（声明 **39 B** / 线上 **39 B** / 校验和 `0x31` / 无转义；`FE 0C = −500`、`01 F4 = 500`、`07 D0 = 2000`）

> 网页在**组帧时**就按这条口径**拒发**：`12 + N > 50` 直接抛错（页内自测 T13 断言「两块 27 B 允许、三块 40 B 拒发，
> 并提示『屏蔽区 `0x29` 每帧最多 2 个』」）。也就是说这条推论在当前实现里已是**硬约束**；
> 但「设备是否真的截断/不识别超过 50 B 的帧」仍待实测（表 B ⑭）。

### 7.9 协议文档里 5 处自相矛盾（如实记录，不替它圆场）

这 5 处都会让实现「看起来能跑、其实错」，逐条给处置与待实测项：

| # | 矛盾点 | 原文怎么写 | 影响 | 本文处置 / 待实测 |
|---|---|---|---|---|
| **a** | **帧尾 `0x0A` 到底要不要** | v1.0 修订记录写「**取消结尾的 0x0A**」，但**帧格式表与全部示例帧仍带 `0x0A`** | 若真按「无帧尾」实现：接收侧等不到结束符、发送侧设备等不到帧尾 → **一帧都通不了** | **按带帧尾实现**（帧格式表 + 4 组示例 + 本例的转义规则都以 `0x0A` 为帧尾才自洽）。待实测：上板看设备是否接受带尾帧（表 B ①） |
| **b** | **波特率** | 「串口通信约定」写 **256000 固定**；但 `0x04` 的出厂默认值是 **4 = 115200** | 桥若按 `0x04` 默认值配 115200 → 收到的是**整段丢字节**（不是乱码） | **桥固定 256000**；`GET 0x04` 回 4 只作「出厂默认没改」的记录，**不要**用 `SET 0x04=5` 去"修正"（改完设备立即换波特率，桥没跟上就失联）。待实测：`GET 0x04` 实际回什么（表 B ①） |
| **c** | **接收方向是否也转义** | 转义注释只说「**只用在发送给模块数据的最后面做处理**，其它地方都不用变」 | 若设备上报不转义而正文含 `0x0A` → 该帧被当帧尾截断（丢 1 帧，可恢复） | **双口径自适应（见 7.3）：同一条候选帧分别按「未转义」与「已转义」还原，取校验和校验通过的一支；单口径无条件还原不安全。** 用「转义对还原数」取证（7.3、7.6）。待实测（表 B ⑨） |
| **d** | **`0x81` 每通道几字节** | 本文依据的 V1.1 原文逐字段就是 **9 字节**（且有 `x/y/z`）；站内水位指南依据的另一份协议/驱动是 **7 字节**（且带 count 前缀） | 混用口径 → 2 通道起整体错位；**单通道时可能"恰好不报错"** | **本文按 9 B/通道**，用 `tlv_len % 9 == 0` 硬判；出现 `1+7N` 或 `1+9N` 一律判口径异常并取证（7.6）。待实测（表 B ④） |
| **e** | **`0x17` 的上报语义** | 「**雷达触发有人后**，每隔所设置的时间上报一次有无人状态」；默认 50（**5 s**） | **无人期间可能完全静默** → 上位机若等 `presence=0` 的帧，会永远显示「有人」 | 用「最后一条帧 + 超时」推断无人（6.4）；演示前把 `0x17` 改成 10（1 s）。待实测：无人时到底静默多久（表 B ②） |

**另有 2 处口径偏差（不算矛盾，但实现时必须选边）**：

1. `0x17` 的示例帧把 value 当 1 字节（`tlv_len=1`），与类型表「2 Byte」不符 —— 本文按 **2 字节**（见 7.5 的说明）。
2. `0x19`「雷达频率」的取值范围写的是 `0: 250MHz 带宽 约 24-24.25GHz / 1: 1GHz 带宽 约 23.5-24.5GHz`，
   而 EDV163 是 **60 GHz** 模组 —— 这段描述明显是从 24 GHz 型号的协议里沿用的。**本版不写 `0x19`**，
   需要用的时候先 `GET 0x19` 回读再决定（表 B ⑬）。

### 8.2 演示前 5 条 SET（按顺序发，逐条等应答）

顺序不能乱：**先把节奏调快 → 再把状态语义调对 → 最后才动几何与调试开关**。

| 序 | 目的 | 帧（含帧尾，脚本生成） | 声明/线上 | 期望应答 |
|---|---|---|---|---|
| 1 | **上报周期 = 1 s**（`0x17=10`） | `45 44 00 0E 00 01 A1 17 00 02 00 09 01 5C 0A` | 14 / **15 B**（含 1 处转义） | `op=A2` 应答（或 `A9` ACK，**仅表示收到、不解释载荷**），回显同 `msgid`；写成功以回读比对为准 |
| 2 | **检测延时 = 3 s**（`0x11=3`） | `45 44 00 0E 00 01 A1 11 00 02 00 03 4F 0A` | 14 / 14 B | 同上 |
| 3 | **触发模式 = 正常运动触发**（`0x24=0`） | `45 44 00 0D 00 01 A1 24 00 01 00 5D 0A` | 13 / 13 B | 同上 |
| 4 | **挂高 = 2500 mm**（`0x25=2500`） | `45 44 00 0E 00 01 A1 25 00 02 09 00 C4 2D 0A` | 14 / **15 B**（含 1 处转义） | 同上 |
| 5 | **调试模式 = 1**（`0x1E=1`，仅为试 `0x80`） | `45 44 00 0D 00 01 A1 1E 00 01 01 58 0A` | 13 / 13 B | 同上 |

**发送纪律**：

- **逐条发、逐条等应答**（`A2` 或 `A9`），单条超时**就停下**——不要连发、不要自动重试三遍（重试会把设备状态搞成猜谜）。
- 某条不回，**先退回发一条 `GET`**（例如 `GET 0x17`）确认通道还在，再决定要不要重发这条 SET。
- 5 条发完后**逐条回读**：`GET 0x17 / 0x11 / 0x24 / 0x25 / 0x1E`，把回读值与设定值并排记进验收记录。
- 网页「**应用演示推荐参数…（需确认）**」发的就是这 5 条（顺序相同），走「**一个总确认框 + 逐条下发 + 逐条回读比对**」。

### 8.3 高危操作与「先回读再 SET」流程

| 操作 | 后果 | 允许的前提 |
|---|---|---|
| `SET 0x1F=1`（恢复出厂） | 所有参数回默认：`0x17`→50、`0x11`→10、`0x1E`→0、`0x25`→默认……**演示现场会突然"没数据、反应迟钝"** | 只在明确要重置时；网页上还要先勾「我已知晓」解锁、再过**两道确认框**（第二道要手动输入 `1F`）。重置后立刻重跑 8.2 的 5 条 |
| `SET 0x04=5`（改波特率） | 设备**立刻**切到 256000，桥没同步就**永久失联**（只能断电重启回默认？——**回不回默认待实测**） | **不要发** |
| `SET 0x18=0`（关雷达） | 射频关闭，一条 `0x81` 都不来，界面只会显示「无人（按静默推断）」 | 明确要停雷达时；记得改回 1 |
| `SET 0x28`（自动测高） | 设备自己改挂高，你的标定被覆盖 | 只在你要放弃标定、接受设备值时 |
| `SET 0x29`（屏蔽区） | 超 2 块/帧会被截断；分帧是否覆盖未知（表 B ⑭） | 单帧 ≤ 2 块，且发完用 `GET 0x29` 回读核对块数 |

**标准写入流程（页面与自研上位机都照这个来）**：

```text
GET 回读当前值  →  与目标值比对  →  在确认框里确认（人看得到「从 X 改成 Y」）
   →  SET 一次  →  等 A2 / ACK（超时即中止）
   →  GET 再回读  →  回读 == 目标值 才算成功，否则记一条「写入未生效」并停止后续
```

| ③ | **`0x80` 是否需要先 `0x1E=1`** | 分两段各 5 min：`0x1E=0` 时 `0x80` 帧数、`0x1E=1` 时 `0x80` 帧数；**判据：后者 &gt; 0 且前者 = 0 → 需要调试模式** | `GET 0x1E` 确认当前值 → 采集 → `SET 0x1E=1` → 再采集 | 两段都是 0 = 该固件不输出 `0x80` → 走 7.7 降级 |
| ④ | **`0x81` 9 B 口径与通道数 1~4** | 每种 `0x13` 取值下采 100 帧，**判据：`tlv_len` 恒 = 9×N 且枚举字节合法** | `SET 0x13` = 1/2/3/4 各采一次（每次改完回读） | 出现 `1+7N` / `1+9N` → 口径与本文不同，立即取证（原始字节存档） |
| ⑤ | **`x/y/z` 符号与坐标系原点** | 人沿 +x 方向移动 1 m，`x` 单调增加且变化量在 **1000 ± 300 mm**；`y` 同理；原点（`x≈0, y≈0`）应落在雷达正下方/正前方 | 地面贴胶带十字，四点往返各 3 次 | 符号相反 → 坐标系定义与假设不同（**不要**在网页端改符号，先取证）；变化量差太多 → 坐标不是 mm 或含比例因子 |
| ⑥ | **挂高 `0x25` 与 `z` 的关系** | 目标不动，`0x25` 从 2000 改到 3000：**若 `z` 平移约 1000 mm → 假设 B（相对雷达）；若 `z` 不变 → 假设 A（相对地面）** | 见 4.3 判别表 | 两种都不是 → `z` 语义另说，别拿去参与判定 |
| ⑦ | **检测延时 `0x11` 实测保持时长** | `0x11=3` 时，「离开 → presence 变 0」的时长在 **3~5 s**（3 s + 一个上报周期余量）；`0x11=10` 时在 **10~13 s** | 秒表 + 事件时间线，各 5 次取中位 | 明显不符 → `0x11` 语义不是「保持秒数」，或 `presence` 位另有延时来源 |
| ⑧ | **30 min 稳定性与坏帧率** | 坏帧率 **&lt; 0.1%**；帧完整率 **≥ 99.9%**；未归属字节率 **= 0**；重同步 ≤ 3 次/30 min | 连续采 1800 s，落原始 `.bin` + 统计 | 任何一项超限 → 先查转义与长度口径，再查线材/供电 |
| ⑨ | **`0x0A` 转义实况** | 统计 30 min 里「还原的转义对数」与「含转义的帧数」；**判据：两者都 &gt; 0，且转义错误 = 0** | 采集时保留原始字节，按 7.3 逐字节还原并计数 | 两者都 0 → 这段数据里根本没有 `0x09`/`0x0A` 数据字节（转义路径没被检验，需补测）；转义错误 &gt; 0 → 设备不转义或长度口径错 |
| ⑩ | **`SET 0x17` 的 value 到底几字节** | 发 2 字节形式（本文，`tlv_len=2`）有应答；`GET 0x17` 回读长度为 **2 B** | 先按本文发；若无应答再试 1 字节形式（协议原文示例） | 只接受 1 字节 → 7.5 的说明要改成「按原文示例」，并把默认值陷阱重新评估 |
| ⑪ | **静止目标是否被判无人** | 人坐着不动 10 min，`presence` 为 1 的帧占比 **≥ 95%**（判据可调，但必须记录） | 静坐 + 事件时间线导出 | 占比低 → 存在检测能力不足，工位/会议室场景不可用（这是人存方案的核心卖点，必须实测） |
| ⑫ | **`0x1D` 30 min 强制无人** | 开 `0x1D=1` 后，连续 31 min 有人场景里出现一次 `presence` 清零 | 长测 35 min（人在场，但保持静止/规律微动） | 不出现 → 该功能未生效；出现 → 长时在席场景必须关它 |
| ⑬ | **`0x19` 频段字段回读** | `GET 0x19` 回 0 或 1（原文只给这两个值） | 回读即可 | 回别的值 → 协议与固件版本不匹配，先别改它 |
| ⑭ | **`0x29` 屏蔽区分批与生效** | 下发 2 块 → `GET 0x29` 回读块数 = 2；再下发 2 块 → 回读是 **4**（追加）还是 **2**（覆盖） | 两轮下发 + 每轮回读 | 覆盖 → 必须一次下发全部（但一帧最多 2 块 → 矛盾，需厂商确认）；不生效 → 屏蔽区坐标口径（Z 是否绝对高度）要重新确认 |
| ⑮ | **侧装 vs 吊装，哪种几何可用** | 两种姿态各采 10 min，比较 `x/y/z` 与实际位移的一致性（判据同 ⑤）与 `z` 是否单调 | 按 4.2 表各装一次 | 侧装 `z` 恒定 → 侧装只能做二维；吊装 `z` 无规律 → 只能当二维用 |
| ⑯ | **浏览器目检（1280×720 / 1920×1080）** | 整页无纵向滚动、四块 UI 不被压扁、日志折叠后画布变高、能量条 40 格对齐 | 两档分辨率各截一次图 | 布局问题（不影响数据正确性，但影响可读性） |
| ⑰ | **`0x02` 设备 ID 回读** | 回 16 B；前 9 B 是设备 ID（可能仍是 `EDQ152_VB`），后 6 B 是固件版本 | `GET 0x02` | 若回的是 `EDV163...` → 说明这批模组改过默认串，本文 8.1 陷阱 ① 的表述要按实际更新 |

## 10. 排障（三层）

### 10.1 三层法：电源与链路 → 帧完整性 → 协议语义

**照顺序走，不要跳层。** 前一层的现象会伪装成后一层的问题，这是现场 90% 的误诊来源：
「没数据」里有八成是电源/接线/波特率，「数据不对」里有八成是转义与长度口径。

### 10.2 第①层 电源与链路（症状：没帧 / 一字节都没有）

| 现象 | 判据（看什么 / 量什么） | 处置 |
|---|---|---|
| 三个灯都不亮 | 主板 3.3 V 没起来 | 换 USB 线（先怀疑充电线）→ 换 USB 口（台式机机箱后面）→ 换主机 |
| 绿灯亮、**红灯不亮** | `3.3V_RADAR` 没建立 | 量 H3 的 `V`/`P` 对 `G` 是否 **3.3 V ±5%**（3.14~3.47 V）；确认模组插的是 **H3** 不是 H4；确认固件把 **IO14** 拉高了 |
| 红灯亮、**一字节都没有** | 供电正常，问题在数据通路 | ① 桥的波特率是否 **256000**（不是 115200、不是 921600）；② 是否插了 H4；③ 是否烧的是透传桥固件；④ 模组固件是否支持这套协议（协议 a/帧尾、b/波特率见 7.9） |
| 设备管理器没有串口 | USB 链路 | 换线 → 换口 → 按住 `BOOT` 再插 USB 后松开 → 关掉其它占串口的软件 |
| 打开端口瞬间板子复位 | DTR/RTS 硬件行为（正常） | 上位机应重试，1~2 s 恢复；**不要**用「一打开必须立刻有数据」做判据 |
| 端口在、设备不在（幽灵设备） | USB 枚举残留 | 拔线等 5 s 重插；设备管理器「显示隐藏的设备」清掉幽灵项再枚举；换线换口；仍不行换主机（先用有源 HUB 排除供电） |

:::tip 一条最容易被忽略的判据
**`GET 0x04` 回 4 不是故障**——那是「出厂默认波特率枚举 = 115200」的记录值，不代表设备现在跑在 115200。
设备实际通信波特率以「能不能收到合法帧」为准；`0x04` 只在你打算改它的时候才有意义（**而本文建议永远别改**）。
:::

### 10.3 第②层 帧完整性 / 有帧没状态（症状：能收到字节，但没有 `0x81`）

| 现象 | 判据（回读什么 / 看什么） | 处置 |
|---|---|---|
| 收到 `45 44`，但**没有 `0x81`** | 回读 `GET 0x18`、`GET 0x1B`、`GET 0x17` | `0x18` 必须 = **1**（0 = 关了射频）；`0x1B` 必须 = **1**（0 = 不触发）；`0x17` 若 = 50（5 s），**先改成 10 再等**——5 s 一帧很容易被当成「没数据」 |
| `0x81` 只在「有人时」才有 | `0x17` 原文是「触发有人后每隔 X 上报」 | 空房间看不到帧**可能是正常的**（表 B ②）；先用「有人」场景验证链路 |
| 有 `0x81` 但 `presence` 恒 0 | 检查检测范围/阈值是否把目标挡在外面 | `GET 0x27`（是否被收窄成很小一块）、`GET 0x26`（检测高度的 max 是否 &lt; 实际目标高度）、`GET 0x14`（是否被改成很短的检测距离）、`0x15/0x16` 阈值是否被调高 |
| 有 `0x81` 但 `tlv_len` 除不尽 9 | 判「载荷口径异常」 | 打印原始 `tlv_len` 与 value 十六进制取证；对照 7.6 判断是 7 B 口径、1+9N 口径还是切帧错位（表 B ④） |
| **多 TLV 帧会被判坏帧** | 协议允许一个帧里**连续多个 `type+length+value`**，而本页**只支持单 TLV** | 收到多 TLV 帧会计一条 `badTlv` → 计入坏帧；这是**已知限制，不是故障**。确实需要多 TLV 就自研解析器按 TLV 循环切，别按坏帧去追 |
| 帧头对、校验大面积失败 | 字节被插入或丢失 | 若同时混着可打印文本 → 固件日志污染（7.4）；否则怀疑接触不良、线太长、H4 |
| 「转义错误」计数增长 | `09` 后跟的不是 `00`/`01`，或按线上字节切帧 | 先修转义（7.3）——转义一错，后面的长度与校验统计都建立在错误切分上 |
| 数据流里出现 `EDK60` / 一行行 ASCII | 固件在打日志 | 零 `printf` + 关横幅 + 运行期日志级别 NONE；**bootloader 日志要单独关**（7.4） |

### 10.4 第③层 协议语义（症状：状态不对）

| 现象 | 判据 | 处置 |
|---|---|---|
| **人走了很久还显示「有人」** | 秒表测「离开 → 状态变 0」时长；回读 `GET 0x11` | `0x11` 默认 **10 s**，会把「有人」保持 10 s（+一个上报周期）。演示建议改 **3 s**（8.2 第 2 条）；判据见 表 B ⑦ |
| **人坐着不动就被判「无人」** | 静坐 10 min 统计 `presence=1` 占比 | `0x16` 存在阈值太高、`0x26` 检测高度把坐姿滤掉、`0x24` 触发模式设成了「靠近/远离」；也可能就是模组静止检测能力不足（**表 B ⑪ 是本方案的核心待测项**） |
| 连续在席被**周期性清零** | 长测 31 min 看是否出现一次 `presence` 归零 | `0x1D`（30 min 强制无人）被打开了 → `GET 0x1D`，工位/会议室场景设 **0** |
| `z` 永远是 0 或乱跳 | 改 `0x25` 看 `z` 是否随动（4.3 判别表） | `0x25` 没设（设备默认挂高与你的安装高度不符）→ `SET 0x25` 为卷尺实测值；若侧装，`z` 本来就可能无效（4.4） |
| 状态在「有人/无人」之间高频跳变 | 事件时间线看跳变周期 | 有人长期不动 + `0x11` 太短；或 G-2 的运动干扰（风口/灯盘/窗帘）；把 `0x11` 调到 3~5 s 观察是否收敛 |
| 「靠近/远离」永远是 0 | 回读 `GET 0x24` | `0x24` 默认 0（正常运动触发）时 `direction` 未必有意义；要它就必须 `SET 0x24=1/2/3` 后再测 |
| 状态一直「有人」且 `x/y/z` 全 0 | 无有效目标但 `presence` 被延时撑着 | 检查是否有静止强反射面（金属柜、玻璃幕墙）、`0x12` 闭锁时间；用 `SET 0x1A=1` 强制清人验证显示链路（然后断电/重启恢复） |
| 卡在自学习状态 | `GET 0x23` ≠ 0 | 发 `0x21`（1 保存退出 / 2 不保存退出）脱身；本方案**不该**进入自学习 |

### 10.5 本方案特有的坑（按杀伤力排序）

| # | 现象 | 根因 | 处置 |
|---|---|---|---|
| 1 | 照抄水位案例的解析器，**单通道能显示、双通道全乱** | 用了 **7 B/通道**（旧口径），本协议是 **9 B/通道**（7.9 d） | 按 `tlv_len % 9 == 0` 硬判；`通道数 = tlv_len ÷ 9`（7.6） |
| 2 | 一切正常，就是**帧里的 `0x0A` 处断开** | 没做转义还原，或按线上字节数切帧 | 先还原 → 再按声明长度切帧 → 再验校验和（7.3） |
| 3 | 界面**永远显示「有人」**，房间明明空了 | 只等 `presence=0` 的帧；而设备无人时可能静默（7.9 e） | 用「最后一条帧 + 超时」推断（6.4） |
| 4 | 演示开始「反应特别慢」 | `0x17` 还是默认 **50 = 5 s** | `SET 0x17=10`（1 s），并回读确认 |
| 5 | 明明通电、却一条 `0x81` 都没有 | `0x18=0`（关了射频）或 `0x1B=0`（不触发） | `GET 0x18` / `GET 0x1B` 回读；两条都要 = 1 |
| 6 | 跑了一次「恢复出厂」后整套参数都回默认 | `SET 0x1F=1`（或误发） | 重跑 8.2 的 5 条；把 `0x1F` 从工具里删掉/加二次确认（8.3） |
| 7 | 屏幕上的点在**隔壁房间** | 波束旁瓣 + 反射 + 检测范围太宽 | `0x27` 收窄 + `0x29` 屏蔽区（≤2 块/帧）+ 调整安装位置（G-1） |
| 8 | 能量条永远是空的 | `0x80` 需要 `SET 0x1E=1`（**待实测**），或该固件不输出 | 按 7.7 的四步降级；不要为了"让图好看"伪造数据 |
| 9 | 串口助手满屏乱码、偶尔蹦出 `ED`，以为坏了 | 这是**二进制协议帧**，不是故障 | 切 HEX 模式；判断链路只看「有没有合法帧」，不看「有没有字」（10.6） |
| 10 | 换了安装高度后 `z` 全乱了 | `0x25` 没跟着改（挂高是坐标参照） | 每次改安装高度都重标 `0x25`，并 `GET` 回读核对（4.3） |

### 10.6 ⚠️ 串口助手看到「乱码」是正常现象

文本模式打开这个端口会看到满屏乱码、方块、`?`，偶尔蹦出 `ED` 两个字母——**这不是故障，是二进制协议帧**：
`0x45 0x44` 正是 ASCII `"ED"`，帧尾 `0x0A` 会被当换行，所以「满屏空白/只有换行」也正常。

**怎么正确看**：切到 **HEX / 十六进制模式**；或者干脆用第 6 节的网页（它懂协议）。
**不要**用「串口助手能看到字」判断链路正常；能不能收数据，只看 HEX 模式里有没有合法帧。

## 11. 已知限制

诚实列出这个方案**没有**做到的地方——照着做之前请先看这一节。

| # | 边界 | 说明 |
|---|---|---|
| 1 | **未实机验证（最大边界）** | 协议拆解、帧字节、网页解析都已按协议核对并做过合成帧自测，但**没有一条上板用例被跑过**。所有「帧率、延时、距离、精度、静止识别率、误报率」类结论**目前都不存在**，本文一处都没编。 |
| 2 | **坐标精度未知** | 协议只给 mm 单位的 `int16`，**没有给分辨率/精度指标**，也没有标定方法。`x/y/z` 目前只能当「相对变化」用，不能当米级定位。 |
| 3 | **无人静默的口径是推断的** | `0x17` 原文只说「触发有人后每隔 X 上报」，无人期间是否发送、发几次没写死。所以「无人」要靠超时推断（6.4），**可能存在最长一个静默周期的滞后**，也可能永远收不到 `presence=0` 的帧。 |
| 4 | **协议文档有 5 处自相矛盾** | 帧尾 `0x0A`（修订记录说取消、示例仍带）、波特率（约定 256000 vs `0x04` 默认 115200）、接收方向是否转义、`0x81` 每通道 9 B vs 站内旧口径 7 B、`0x17` 无人静默语义。本文逐条给了处置（7.9），但**最终定论都要等实机**。 |
| 5 | **侧装 vs 吊装还没定** | 产品页写侧装 0.5-1.8 m，协议的 `0x25/0x26/0x27` 按俯视设计。哪种姿态适合你的项目**必须实测**（4.2、表 B ⑮）；侧装下 `z` 很可能无效。 |
| 6 | **`0x80` 能量帧可能拿不到** | 它叫「调试数据输出」，是否需要 `SET 0x1E=1`、是否默认关闭、是否会随时被固件关掉，全部待实测（7.7）。拿不到就走降级路线，**不要伪造能量数据**。 |
| 7 | **多通道语义未验证** | `0x13` 允许 1~4 通道，但「通道顺序 ↔ 物理位置」没有任何说明（协议不给通道号）。多通道只做了载荷长度校验，**没做通道融合/合并/去重**。 |
| 8 | **`0x02` 不能用来判型号** | 出厂默认设备 ID 仍是 `EDQ152_VB`（这份协议是「替换 EDQ152 通用协议」）。拿 `0x02` 判断「是不是 EDV163-N-03」会误判（8.1 陷阱 ①）。 |
| 9 | **`0x15`/`0x16` 阈值与自学习未使用** | 阈值分距离门，原文没给默认值，改错会「静默把目标滤掉」；`0x20~0x23`（自学习）语义与副作用未知，本版**全部不发**。 |
| 10 | **50 B 上限只给到推论** | 「一帧最多 2 块屏蔽区」是由 50 B 上限推出来的，且 50 B 按转义前还是转义后计、分帧下发是追加还是覆盖，原文都没说（7.8、表 B ⑭）。 |
| 11 | **只有网页这一种上位机** | 没有桌面端工具；页内自测可用 `node scripts/edv163_presence_selftest.mjs` 在无浏览器环境复跑，但它**不是抓包/统计工具**。要长期统计只能自研，规则见 7.1 / 7.3。 |
| 12 | **浏览器限制** | Web Serial 只在 **Chrome / Edge 89+** 可用，且需 **https 或 localhost**；Firefox / Safari 不支持。页面不写本地存储、不导出 CSV、不截图，刷新即清空。 |
| 13 | **没有长期与极端环境数据** | 计划里最长用例是 30 min（表 B ⑧），**没有 24 h / 7 天**，没有温漂、结露、强光、强电磁干扰下的结论；也没有功耗/电流实测数据。 |
| 14 | **不承担安全与生命相关结论** | 这是技术演示：人存判断来自雷达算法输出，未经功能安全评估，**不得用于安防报警、消防、生命监护、门禁安全联锁等任何有责任后果的场景**（见文末免责声明）。 |
