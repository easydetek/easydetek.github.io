在一个小盒子里塞一颗 60 GHz 雷达，让它在**不接触、不按键、不掏手机**的前提下识别「向左挥 / 向右挥 / 向上挥 / 向下挥」，
并在手靠近到 20 cm 时给出一个**触发**——这就是 **EDV163 挥手识别（手扫）** 模组能做的事。

我们用 **EDK60 开发板**（ESP32-C6）把它桥到 **芯片原生 USB**：模组每 40~43 ms 吐一行可读文本，
ESP32-C6 把串口字节**原样**搬到 USB，浏览器打开一个单文件网页，就能看到**挥手方向大字 + 目标坐标 + 距离触发 + 两个位置视图**。
不需要 USB 转串口芯片、PC 端不需要装任何驱动。

> **✅ 验证状态（必读）**：**2026-10-23 已上板跑通**——EDK60 桥 + EDV163 挥手固件，
> USB 直连浏览器与本机工具均可用。本文里的行率、坏行率、方向映射、动作轴映射、坐标范围、距离触发都是**实测值**；
> 仍标着「待实测」的只剩 5 项：`0x4544` 点云帧占比（三次采集 0 帧）、`±3` 极性（从未出现）、
> `target=0` 的精确时延、长时稳定性（最长 75 s）、浏览器像素级目检。
> 协议结论仍来自**厂商上位机源码逆推**（没有协议文档），样例行取自厂商 README、不是我们的抓包。

## 场景需求

| 需求 | 说明 | 方案如何满足 |
|---|---|---|
| **非接触** | 场景常是「手上有水/戴手套/不想碰公共表面」 | 60 GHz 雷达看手部运动轨迹，**零接触** |
| **不要专用硬件面板** | 加一个实体按钮就要开孔、要防水、要防误触 | 一颗模组嵌在产品内部，外观完整、无开孔 |
| **看得懂「方向」** | 只知道「有人挥手」不够，翻上/下一页需要**上下**，切上下曲需要**左右** | 模组直接输出 `action` 编码：`-2/-1/0/1/2` 对应下/右/无/左/上 |
| **还能当接近开关** | 手伸过来才响应，避免远处路过的人误触发 | `target=1` 且 `z` 小于阈值（默认 20 cm）才算「触发」 |
| **免驱动接入** | 现场/演示电脑常是受控环境，不能装驱动 | ESP32-C6 原生 USB CDC，插上就是串口 |
| **上位机可替换** | 客户可能要把数据接进自己的平台 | 桥接固件**纯字节透传**，不解析、不加工；文本协议公开，谁都能写上位机 |
| **不依赖云** | 隐私敏感场景不想把「有人在场」传到云端 | 全链路本地：模组 → 板子 → 浏览器，无网络请求（页面无 `fetch` / 无外链） |

**为什么选雷达而不是摄像头或红外**：摄像头有隐私顾虑且需要算力；红外只能判「有/无遮挡」，分不出**方向**。
60 GHz 雷达能给出目标的 `x/y/z` 与运动方向编码，一颗器件同时解决「接近检测 + 手势方向」，且**不采集任何图像**。

## 方案构成

```text
EDV163 60 GHz 雷达模组（挥手识别固件 163_action_20260901）
   │  UART 115200 8N1（模组 TX → IO4）
   ▼
EDK60（ESP32-C6）——纯字节透传：不解析、不切行、不跳帧、不映射、不算触发
   │  芯片原生 USB CDC（免驱动）
   ▼
浏览器（单文件网页）：跳 0x4544 点云帧 → 按 \n 切行 → 六条正则 → action 映射 → 触发判定
```

| 环节 | 器件 / 技术 | 关键点 |
|---|---|---|
| 感知 | EDV163（挥手固件 `163_action_20260901`） | 实测每 **40~43 ms** 输出一行文本：`GESTURE: target=… x=… y=… z=… action=…`；流里按厂商设计还混着 `0x4544` 二进制点云帧（实测三次采集 0 帧） |
| 主控 | ESP32-C6（EDK60_VA V1.0） | UART1 收模组（**115200** 8N1），原生 USB 发给 PC，两路各自独立 |
| 连接 | 芯片原生 USB Serial/JTAG | 省掉 USB 转串口芯片与驱动；USB CDC 本身不受波特率限制，填 115200 只为与线速对齐 |
| 供电 | PC 的 USB-C 口 | 模组低功耗（水位版规格为 11 mA 量级），PC 口足够；**不需要**外部适配器 |
| 上位机 | 单文件网页（Web Serial） | **完全只读**：不取 `port.writable`、无 `.write(`、无 `getWriter()`；调试 API 被 `Object.freeze` |

## 接线

| 信号 | EDK60 侧 | 模组侧 | 说明 |
|---|---|---|---|
| 模组 TX → MCU RX | **IO4** | H3 排针 `T` 脚 | **本方案唯一的信号线**（数据全靠它） |
| 模组 RX ← MCU TX | **IO5** | H3 排针 `A` 脚 | **本方案不发命令**（模组无命令接口），固件保留通路但常态空闲 |
| 雷达电源使能 | **IO14**（高有效） | — | 上电后常高；丝印 `RADAR` 红灯 = 已上电 |
| 电源 / 地 | `3.3V_RADAR` / `GND` | `V`、`P` / `G` | 3.3 V 单电源，**不需要电平转换** |
| 串口参数 | **115200 / 8N1**，无流控 | — | **不是**人数统计版的 921600，也**不是**水位版的 256000 |

:::warning 模组必须插 H3，不要插 H4
板上 H3 与 H4 两个 8 pin 排针**信号集合相同但顺序相反**：
H3 = `RES A R T G V P`，H4 = `RES P V G R T A`。
H4 的 `T` 脚与雷达电源使能在同一侧的网络关系上，插 H4 会让电源与数据互相干扰，
症状是「红灯亮着、却一个字节都没有」或「偶发丢行」——最难查的那一类。
另外：**禁止在雷达已上电（红灯亮）时插拔模组**。
:::

## 关键工程点

### 1. 没有协议文档时，怎么把协议「逆推」到可用

这是本项目最不寻常的一步：**厂商只给了一个上位机程序（Python + Tkinter，774 行）和一份 README，没有协议文档。**
我们的做法不是「猜」，而是**把源码当成规格书**：

| 做法 | 具体怎么落地 |
|---|---|
| **只认源码，不认二手转述** | 行格式来自模块 docstring 与 `GESTURE_RE`；`action` 编码来自 `WAVE_ACTION_INFO` 字典；位置图语义来自 `TargetPositionPlot._redraw`；触发判定来自 `_refresh_trigger_status`。**每一处在文档里都标行号**，方便下次换固件时逐行复核 |
| **把「容错」也照抄，不只抄格式** | 厂商的二进制帧跳过逻辑里有四个判定（帧头优先 vs 换行优先、长度 11~4096、累加校验、**校验失败只丢 1 字节**）。少抄最后一条，一个假帧头就会吞掉后面几秒的文本 |
| **兼容分支照抄，但不当主路径** | 源码有 6 条正则（正式行 + 旧双通道 + 四种 `DBG:`），匹配顺序也照抄。它们可能全是死代码，但**「看到调试行出现」本身就是信号** |
| **把「源码没证明的事」单独列成清单** | 当初整理了 **9 条未确认项**：点云帧是否真的存在、`action` 四向符号是否有物理验证、`±3` 的极性、`target=0` 的时延、`lock` 是否需要显示……每一条都写了「为什么必须确认」与「怎么确认」。**2026-10-23 上板后**，方向符号与行率/坏行率/坐标这几条拿到了实测答案，点云帧与 `±3` 得到「三次采集均未出现」的负结果，其余仍如实标着待验证 |
| **用自测把「逻辑正确」与「物理正确」分开** | 110 项对账能证明「同样的字节进来，解析与判定不会错」；它**不能**证明「真实模组真的发这些字节」。这两件事混在一起讲，就是过度宣称 |

代价与风险要说清楚：**逆推的协议是「对某一版源码成立」的**。模组固件一换（本项目就从水位版的 256000 二进制换到挥手版的 115200 文本），
格式就可能变。所以文档里明写「以源码为准」，并把**坏行率**当成洁净度指标：坏行率一旦超过 1%，先怀疑格式变了或日志污染，不要先怀疑雷达。

### 2. 文本 + 二进制混流：为什么「桥什么都不做」反而是最稳的

本方案的串口流不是单一形态：**主体是文本行，中间还会插二进制点云帧**。这带来一组很反直觉的结论。

**先说危险在哪**：

| 危险 | 说明 |
|---|---|
| **文本行没有长度、没有校验** | 多一个 `\r` 就匹配失败、少一个字节就和下一行粘连，而且**没有任何机制能发现** |
| **二进制载荷里也有 `0x0A`** | 只按换行切行，会把后面的 `GESTURE:` 行撕成两半 |
| **载荷里也可能有 `0x4544`** | 所以「见到 `0x4544` 就当帧头删掉」会删掉真数据 |
| **污染没有明确信号** | 上位机解析不出就静默丢弃 → 现场只看到「挥手方向偶尔不显示」 |

**再说为什么必须「整帧跳过 + 丢 1 字节重同步」**：厂商给出的规则是四件事一起做——
① 比较「第一个换行」与「第一个 `0x4544`」谁先出现；② 长度字段必须落在 11~4096；
③ 前 `total-1` 字节求和取低 8 位必须等于末字节；④ **校验失败只丢 1 个字节**再重新同步。
第④条是关键：如果按声明的长度整段跳过，一个假帧头（长度字段是垃圾）就会把后面几秒的文本一起吃掉。

**最后说为什么这些逻辑一行都不能放进固件**：

| 如果桥上「顺手处理」 | 后果 |
|---|---|
| 过滤 `0x4544` 帧 | 载荷里的 `0x4544` 会被误判；删掉的是**真点云数据**；而且这四条规则合起来已经是一个完整解析器，搬进固件就是**协议知识复制两份**，两份必然漂移 |
| 加换行 / 加前缀 / trim | 文本协议**没有校验**，任何多余字符都让那一行废掉，且现场查不出来 |
| 攒整帧再转发 | 增加延迟、增加内存、还得跟着模组固件改——**模组换固件就要重烧桥** |

所以设计铁律是：**桥只允许改变「字节到达的时刻」，不允许改变「字节本身」。**
本项目换机型（水位 256000 二进制 → 挥手 115200 文本）时，固件只改了波特率一行宏——这就是这条铁律的回报。

**代价**：固件必须做到「零字符输出」。五道保险 + 一道门禁（日志级别编译期消失、横幅/引脚表关闭、
源码零 `printf`、运行期把日志级别设成 NONE、bootloader 日志级别关闭、分派表里整块跳过横幅），任何一道漏了，
USB 上就会多出一行日志——**它不会被当成日志，只会被当成坏行**。

这不是理论风险：**2026-10-23 首次上板就真咬到了**——`I (115) esp_image: segment 3: ...` 混进了 USB 流。
上面五道全都拦不住它，因为 **bootloader 阶段的日志不受 `CONFIG_LOG_DEFAULT_LEVEL` 管**。
补上 `CONFIG_BOOTLOADER_LOG_LEVEL_NONE=y` 后复测通过，坏行率回到 0.00%~0.35%——
剩下的那点坏行不是我们的锅：模组每次上电自己会吐 `EasyDetek` 与 `EDV163_VB_ID0xFFFF_V101` 两行 banner。

### 3. 挥手方向 + 距离触发能做什么（以及它不能做什么）

`action` 编码只有 5 个有效值（`-2` 下 / `-1` 右 / `0` 无 / `1` 左 / `2` 上），另有 `±3` 表示靠近/远离（**厂商界面不显示**）。
这个极简的编码，配上 `target`（位置是否有效）与 `z`（距离），刚好够做三类交互：

| 交互类型 | 用到的信号 | 典型产品形态 | 注意 |
|---|---|---|---|
| **左右切/翻** | `action = 1 / -1` | 相框、菜单、PPT 翻页、歌单切换 | 一次挥手 = 一次事件；必须做**去抖**。实测一次挥手会连续触发 **6 行**相同 `action`（约 0.23 s），每行都当事件就会连跳 6 页 |
| **上下调** | `action = 2 / -2` | 亮度/音量/档位上下调 | 上下挥手与「抬手遮挡」在点云上容易混，建议配合距离门限 |
| **无接触接近开关** | `target = 1` 且 `z` 小于阈值（默认 20 cm） | 手伸到设备前 20 cm 内点亮/唤醒/激活 | 阈值 0~100 cm 可调；**「触发」是状态而非事件**，产品侧要自己做边沿检测 |
| **存在感知（附带）** | `target = 0 / 1` | 无人时降亮度/休眠 | `target=0` 的含义是「位置窗未形成」，**不等于「绝对没人」**，别单独拿它做安防 |

**它不能做的事**（写清楚，免得被当成万能手势方案）：

- **不能自定义手势**：模组只认这 4 个方向，画圈、捏合、双击都识别不了；
- **不能识别多人**：单目标，取的是雷达视野里的主目标；
- **不输出点云**（在本方案里）：`0x4544` 帧只被整帧跳过，没有做可视化与二次算法；
- **不是精密定位**：`x/y` 显示量程只有 ±0.40 m，坐标是设备给的浮点值，**不代表毫米级精度**；
- **方向符号已实测核对**：`action` 的映射表来自源码，但 2026-10-23 已用现场目视核对过一遍（显示方向与实际一致），
  `±1` ↔ X 轴、`2` ↔ Y 轴也按 `Δx/Δy` 统计确认。

### 4. 一个容易被忽略的细节：坐标 `x` 为正时显示在左边

厂商的 X-Z 俯视图把雷达放在下方中心、`z` 向前，**雷达坐标系里 `x` 为正的目标画在图的左侧**；X-Y 正视图同样如此、`y` 为正向上。
这与「目标往右走，红点往右走」的直觉相反。我们照抄了厂商语义（源码注释与坐标变换都能对上），
理由很简单：**这是给同一颗模组做对照的工具**，语义分叉会让「网页看到的」与「厂商界面看到的」永远对不上，
之后所有现场排查都会多一层怀疑。

### 5. 挥手动画与锁定期：让「一次检测」只播一次动画

界面上的「挥手方向大字」之外，网页加了一层**手掌滑动动画**：左挥 → 掌从左到右，右挥 → 右到左，
上挥 → 下到上，下挥 → 上到下，时长 **2.5 s**（含 300 ms 淡出）。

但实测数据说明，光有动画会翻车：**一次挥手会连续触发 6 行相同 `action`（约 0.23 s）**。
所以动画外面套了一层「**锁定期**」：

| 规则 | 做法 |
|---|---|
| 锁定期内的展示 | **冻结**：不重启动画、不切换动作名 |
| 锁定期内的统计 | **照常**：行率 / 有效行 / 坏行 / 坐标 / 日志 / 直方图继续累计，一帧不丢 |
| 锁定期内被抑制的动作 | 单独计数，界面显示「**动画期忽略 N**」，不静默丢弃 |
| 同一次检测的去重 | 相邻行间隔 **≤300 ms** 且 `action` 同值 ⇒ 视为残留帧，**不重复播放** |
| 无障碍 | `prefers-reduced-motion` 时退化为**静态手掌 + 800 ms 淡入淡出** |

一句话：**锁定期只冻结「展示层」，不冻结「解析层」**。
这是有意为之——手势是给人看的，统计是给排查用的，前者要不抖，后者不能缺。

## 已知限制

写清楚没做的部分，比写清楚做了的部分更重要：

| 限制 | 现状 |
|---|---|
| **仍有 5 项未验证** | 2026-10-23 已上板跑通，行率/坏行率/方向/动作轴映射/坐标/触发均为实测；仍未验证：`0x4544` 点云帧占比（三次采集 0 帧）、`±3` 极性（从未出现）、`target=1→0` 精确时延、长时稳定性（最长 75 s）、浏览器像素级目检 |
| **没有协议文档** | 全部协议结论来自厂商上位机源码（774 行）+ README，逐处标了行号；固件换版本格式可能变 |
| **文本协议对污染零容忍** | 一条 `printf` 就能吃掉文本行完整性；工具只能检测（坏行率/重同步），不能预防；根治在固件零字符输出 |
| **二进制帧只跳过、不解析** | 不做点云可视化；三次采集 **0 帧**，该分支目前是防御性代码、从未被真实数据走过 |
| **方向编码已实测、但仍属源码语义** | 左=1/右=−1/上=2/下=−2 已现场目视核对通过；换固件后若全反，属固件/协议问题，**不要在网页端改映射** |
| **`±3` 极性仍是推断** | 按「距离减小 = 靠近」推断；三次采集**一次都没出现**，这行小字目前没有真实数据 |
| **`lock`（动作锁）不显示** | 与厂商界面一致；产品若要，应加只读标签而不是改解析 |
| **行率不可调** | 实测 **40~43 ms/行（24.3~26.5 行/秒）**，是模组固件行为；链路无命令接口，桥只能透传 |
| **模组开机固定吐 2 行 banner** | 每次上电模组输出 `EasyDetek` 与 `EDV163_VB_ID0xFFFF_V101`，会被计为坏行——坏行率 0.00%~0.35% 的唯一来源，**属模组侧，改不了** |
| **设备 ID 是 0xFFFF（未写入）** | 自报版本串 `EDV163_VB_ID0xFFFF_V101`：设备 ID 仍是出厂未写状态、固件 V101；多模组场景不要当唯一标识 |
| **坐标不是精度指标** | 3 位小数只是显示精度；实测范围 x ∈ [−1.21, +0.20]、y ∈ [−0.28, +0.57]、z ∈ [0.06, 1.14] m；真实精度需另设工装标定 |
| **网页不落盘** | 不写本地存储、日志 400 行上限、刷新即清；要留证据用命令行工具 `--save-raw` / `--csv` |
| **浏览器限制** | Web Serial 只在 Chrome / Edge 89+ 可用，需 https 或 localhost；Firefox / Safari 不支持 |
| **不承担安全/控制责任** | 挥手方向与距离触发未经功能安全评估，不可直接用于门禁、医疗、机械控制等有安全后果的场景 |
