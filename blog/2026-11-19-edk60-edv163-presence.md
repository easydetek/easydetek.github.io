**「人还在不在」和「人动不动」是两个问题**，而便宜的存在检测大多只回答后一个：PIR（热释电红外）测的是红外辐射的**变化量**，
人一坐定、变化量归零，它就判「无人」——自习室、办公位、卫生间隔间的灯，正是在人坐着的时候自己灭掉的。
毫米波雷达看的是**微动与呼吸引起的胸廓起伏**（毫米级位移），所以它的**设计目标**是：静止的人依然有回波、依然有周期性起伏，
静坐也应判为「有人」。**但这一点尚未实测**——它是本文「待实测」表里最重要的那一项，判据写在表里（静坐 10 min，`presence=1` 帧占比 ≥ 95%），
在拿到实物跑完之前，它只是设计目标，不是结论。

**EDV163-N-03** 把这件事做成「一条报文说清」：主动上报 `op=0xA3 / type=0x81`，**固定 9 字节、单目标**，
一次就给出**有人/无人 → 无人·静止·运动 → 静止·靠近·远离 → X / Y / Z 坐标**（X、Y 是 int16，Z 是 **uint16**，单位 mm）。
我们用 **EDK60 开发板**（ESP32-C6）把它桥到**芯片原生 USB**：模组串口字节**原样**搬到 USB，
浏览器打开一个单文件网页就能看到「有人/无人」大字、目标坐标与 X-Y 俯视图；无 USB 转串口芯片、PC 端不装驱动、不上传任何数据。

> **✅ 验证状态（必读）**：**2026-11-19 已上板跑通首轮**（模组自报 `EDQ163_VB` / 固件 `V2.1.0`）：
> V1.4 帧稳定流入、`0x81` 全部 9 B 单目标、上报周期实测 **5010 ms**（对应 `0x17=50`）、
> 会话内 **33 帧 0 坏帧 0 未归属字节**、有人↔无人可翻转（详见下「真实状态」）。
> 但那只是**单点、约 3 分钟、33 帧**的一次会话：**帧率上限、坏帧率长期水平、检测范围/角度精度、响应延时、
> 静止识别率、电流这六类指标本文仍然一个数都没有**，全部标着「待实测 + 判据」。
> 协议按《EDV163-N-03 串口通信协议 V1.4（2026-11-04）》**全文逐条**核对，并与工程师上位机 `edv163_serial_tool_V1.0` 交叉验证；

## 场景需求

| 需求 | 说明 | 方案如何满足 |
|---|---|---|
| **静坐也要被感知** | 人坐着不动（看屏幕、开会、如厕）时不能判「无人」 | 雷达看微动与呼吸级起伏；`0x81` 第 2 字节把「静止」单列一档（0 无人 / 1 静止 / 2 运动），不用靠运动量硬猜。**这一条是设计目标，待实测** |
| **非接触** | 卫生间、隔间、病房不适合装要被人碰的东西 | 60 GHz FMCW，**零接触**，不采集任何图像 |
| **无机械件、免维护** | 现场没人愿意擦探头、换电池、爬上去重新对准 | 无镜头、无运动部件、无易损件 |
| **单台覆盖一个工位或隔间** | 点位越少越好装、越好维护 | 检测范围（`0x27`，8 个 int16）、检测高度（`0x26`，上下限）、屏蔽区（`0x29`，最多 10 个）都能下发 |
| **免驱动接 PC 看数据** | 现场电脑常是受控环境 / 云桌面 | ESP32-C6 原生 USB CDC，插上就是串口 |
| **上位机可替换** | 客户已有自己的网关或平台 | 桥接固件**纯字节透传**（不解析、不组帧、不转义）；协议公开，谁都能写上位机 |

**为什么这一档要谈「状态参数」而不是「触发」**：人存要回答的是「现在有没有人」这个**持续状态**，所以 V1.4 给的是一组时间语义——
`0x12` 闭锁时间（无人后允许重新进入有人需要等待的时间，默认 2 s）、`0x17` 状态上报频率（默认 50 = **5 s**）、
`0x1B` 触发使能（默认 1）、`0x24` 触发模式（默认 0 = 正常运动触发）、`0x1D` 30 min 强制进入无人（默认 0）。
它们不是可有可无的调参项，而是**「人走了多久才算走」的定义**：把 `0x12` 调到 60 s，灯就会在人走后还亮一分钟；
把 `0x1D` 打开，长时间静坐（看书、陪护、午睡）可能被强制清成「无人」。

## 方案构成

```text
EDV163-N-03 60 GHz 人存雷达模组（侧装或吊装，天线朝向被检测区）
   │  UART 256000 8N1（模组 TX → IO4，模组 RX ← IO5）
   ▼
EDK60（ESP32-C6）——纯字节双向透传：不解析、不组帧、不转义、不代发命令
   │  芯片原生 USB CDC（免驱动）
   ▼
浏览器（单文件网页）：按「帧头 + 长度字段」切帧 → 校验和 → 解 0x81（9 B 单目标）
```

| 环节 | 器件 / 技术 | 关键点 |
|---|---|---|
| 感知 | EDV163-N-03（60 GHz 人存雷达，协议 **V1.4**） | `0xA3/0x81`：**固定 9 B 单目标** = 有人 0/1 + 无人/静止/运动 + 静止/靠近/远离 + X int16 + Y int16 + Z **uint16**（大端，mm） |
| 主控 | ESP32-C6（EDK60_VA V1.0） | UART1 与模组通信（**256000 固定** 8N1），原生 USB 与 PC 通信，两路各自独立 |
| 连接 | 芯片原生 USB Serial/JTAG | 省掉 USB 转串口芯片与驱动；USB CDC 对波特率不敏感，填 256000 只为与线速对齐 |
| 供电 | PC 的 USB-C 口 | 3.3 V 单电源由板载 LDO 供，**不需要外部适配器**（峰值电流待实测，判据 &lt; 300 mA） |
| 上位机 | 单文件网页（Web Serial） | **默认只读**：连上只发 13 条 GET；写参数必须逐条确认、并等应答 |

两条与「看数据」直接相关的口径，先说清楚免得白折腾：

1. **一条 `0x81` 就是一个目标，没有「通道」概念**：V1.4 已删除 `0x13`（检测通道数量），也删除了 `0x80`（调试能量帧）。
   所以不存在「每通道 9 B / `tlv_len` 能整除 9 推出通道数」这套算法，更没有 40 个距离门可以画能量柱——
   想要「能量/活动随时间怎么变」，只能自己把 `0x81` 的坐标流累积成轨迹（演示页就是这么画的）。
2. **桥接固件不参与协议**：V1.4 **无帧尾、不转义**，切帧只靠「帧头 + 长度字段」，所以纯字节透传才是对的；
   固件一旦试图「帮忙」按 `0x0A` 切分或做转义还原，反而会造出坏帧。

## 接线与安装

| 信号 | EDK60 侧 | 模组侧 | 说明 |
|---|---|---|---|
| 模组 TX → MCU RX | **IO4** | H3 排针 `T` 脚 | 数据入口（状态与坐标全靠这条线） |
| 模组 RX ← MCU TX | **IO5** | H3 排针 `A` 脚 | 下发配置（`0x17` 频率、`0x12` 闭锁、`0x25` 挂高、`0x29` 屏蔽区） |
| 雷达电源使能 | **IO14**（高有效） | — | 上电后常高；丝印 `RADAR` 红灯 = 已上电 |
| 电源 / 地 | `3.3V_RADAR` / `GND` | `V`、`P` / `G` | 3.3 V 单电源，**不需要电平转换** |
| 串口参数 | **256000 / 8N1**，无流控，**大端** | — | V1.4 原文「波特率 256000 固定」，且**没有**波特率命令可改，256000 是唯一口径 |

:::warning 模组必须插 H3，不要插 H4；禁止带电插拔
板上 H3 与 H4 两个 8 pin 排针**信号集合相同但顺序相反**：H3 = `RES A R T G V P`，H4 = `RES P V G R T A`。
H4 的 `T` 脚与雷达电源使能在同一侧的网络关系上，插 H4 会让电源与数据互相干扰，症状是「红灯亮着、却一个字节都没有」或「偶发丢帧」——最难查的那一类。
另外**禁止在雷达已上电（红灯亮）时插拔模组**，热插拔会同时打电源与 UART 两条线。
:::

| 项 | 侧装（产品页口径 **0.5~1.8 m**） | 吊装俯视（人存常见做法 **2.4~3 m**） |
|---|---|---|
| 姿态 | 装墙面/立柱，天线朝水平方向 | 装天花，天线朝正下方 |
| 对「静坐」 | 视线能照到躯干（胸腹起伏面最大），几何上更有利 | 只照到头顶与肩，呼吸起伏的投影面积小 |
| 遮挡 | 隔断、屏风、立柱会切扇区 | 天花板方向无遮挡，但桌面、吊柜会挡 |
| 坐标含义 | `x/y` 是水平面内位移，`z` 的物理含义待实测 | `z` 最可能 ≈ 离地高度（推断） |
| 主要风险 | 正面贴装时的近场盲区；远距离波束变宽 | 挂高与检测高度设错 → `z` 全错、扇区漏检 |

两种安装孰优**取决于检测范围的实测**，本文给不出结论（判据见「待实测」表里「侧装 vs 吊装」那一行）。

**`0x25`（挂高）与 `z` 的关系**：`0x25` 是 1200~5000 mm 的系统参数，而 `0x29` 屏蔽区的约束写的是 `0 < Z < 挂高`，
说明 **`z` 的量程上限就是挂高**；由此推断 `z` 从安装基准（地面）向上量、吊装时 ≈ 离地高度——这是**推断不是结论**。
验证办法：蹲下/站起各采 30 s，看 `z` 是否跟着人高变化；同时确认 `z` 的上限是否等于 `GET 0x25` 的回读值。
注意 `Z` 在 `0x81` 里是 **uint16 无符号**（`FF FF` = 65535）；`0x27` 检测范围**只有 X/Y**（8 个 int16，没有 Z 字段），而 `0x29` 屏蔽区的边界里 Z 是 **int16 有符号**——同一份「Z」，`0x81` 与 `0x29` 两处符号规则不同，别用同一段解析代码。

### 首轮上板实测（2026-11-19，单点 · 约 3 分钟）

条件：EDK60 + EDV163-N-03（模组自报 **`EDQ163_VB`** / 固件 **`V2.1.0`**），纯字节透传桥固件，室内单人次；
未刻意布置几何（`0x25` 沿用回读到的 3000 mm、`0x27` 沿用默认 ±3000），**未做**静坐 10 min / 长稳 / 精度标定。

| 观察项 | 实测结果 |
|---|---|
| 链路（V1.4 帧） | **通**。`45 44 00 14 00 01 A3 81 00 09 01 02 01 …`——20 B、`len = 00 09`、**末字节是校验和、没有 `0x0A` 帧尾** |
| 只读回读 | 13 条 GET 中 **12 条**即时应答：`0x01` 协议版本 0 / 厂商 `ED`；`0x02` = `EDQ163_VB` / `V2.1.0`；`0x12` = 2 s；`0x17` = 50；`0x18` = 1；`0x25` = 3000 mm；`0x27` = ±3000；`0x29` = 0 块 |
| 帧完整性 | 总字节 **595**、帧数 **33**、`0x81` **20** 条、坏帧 **0**、未归属字节 **0**、校验和错 **0**、帧头重同步 **0** |
| 上报周期 | 帧间隔 **5010 ms**，与 `0x17 = 50`（5 s）一致 |
| `0x81` 口径 | 全部 **9 B 单目标**，无多通道字段 |
| 有人↔无人 | 观察期内「有人 → 无人」（维持 15 s）与「无人 → 有人」各一次，状态卡 / 事件时间线一致 |
| 坐标 | 例：`x = −12 mm、y = 505 mm、z = 826 mm`（另有 `x = 308 / y = 564 / z = 845`），`z` 落在 `0`~挂高 3000 mm 内 |

**一句话**：主链路（帧格式 → 9 B 单目标 → 回读 → 上报周期 → 有人/无人翻转）在实物上成立；
**性能指标仍然全部未知**——样本只有 33 帧 / 约 3 分钟，**别把这里的「0 坏帧」当成长期指标**。

| 30 min 稳定性与坏帧率 | 没上板 | 坏帧率 `&lt;` 0.1%、帧完整率 ≥ 99.9%、未归属字节率 = 0、校验和错 = 0（口径沿用站内水位指南，便于横向对照） |
| 侧装 vs 吊装 | 两种几何都要实装 | 同一位置各打 10 个点（0.5/1/1.5/2/2.5/3 m × 静坐/站立）出「检出/漏检」表；判据不是「谁更远」，而是**静坐 30 min 出现几次误判无人** |
| 屏蔽区 `0x29` 的「覆盖 vs 追加」 | 协议只给字段定义，没写多次下发的语义 | 一次下发 10 个后 `GET 0x29` 回读；再分两帧各 5 个下发后回读：回读 10 个 ⇒ 追加；只回 5 个 ⇒ 覆盖（分批就无效） |
| `0x28` 自动测高改了什么 | 原文只写「约 5 s 后恢复正常工作」 | `SET 0x28=1` 后等 6 s，对比前后 `GET 0x25` / `GET 0x26` 的回读值；记录是否写入实测高度 |
| 峰值电流与上电时序 | 没上板 | 峰值电流 `&lt;` 300 mA；`3.3V_RADAR` 上升时间 `&lt;` 50 ms；两者与 `IO14` 拉高时刻一起录波 |

## 关键工程点

### 1. 帧格式换代了：`12+N` + 帧尾 `0x0A` + 转义 → `11+N`、无帧尾、不转义

V1.1 与 V1.4 **帧格式不兼容**。V1.4 原文两句关键的话：「本协议直接传输完整原始帧，**不进行字节转义**；数据域中的 `0x09` 和 `0x0A` 保持原值」，
以及修订记录 1.0 就写了的「取消结尾的 `0x0A`」。同一套规则下，V1.1 的 10 条命令（`0x04`/`0x11`/`0x13`/`0x14`/`0x15`/`0x16`/`0x19`/`0x1C`/`0x1E`/`0x80`）在 V1.4 里已被删除。

| 项 | 旧口径（V1.1） | **V1.4** |
|---|---|---|
| 长度字段 | 整包 = **12 + N**（N 为转义前 value 字节数） | 整包 = **11 + N**（N 为 value 字节数） |
| 帧尾 | 恒有一个 `0x0A` | **没有帧尾**，末字节是校验和 |
| 转义 | `0x0A → 09 01`、`0x09 → 09 00` | **不转义**，`0x09` / `0x0A` 原样 |
| 切帧依据 | 长度字段 + 帧尾 | **帧头 + 长度字段**（`45 44` 可能出现在 Value 里，不能靠搜帧头） |
| 校验和 | 帧头到 value 末（转义前）求和 mod 256 | 帧头到 Value 末逐字节求和 mod 256 |

拿最简单的 `SET 0x17 = 10`（上报周期 1 s）对照，同一个动作在两种口径下字节数都不一样：

```text
旧口径（V1.1）：45 44 | 00 0E | 00 01 | A1 | 17 | 00 02 | 00 09 01 | 5C | 0A   ← 声明 14 B、线上 15 B、校验 0x5C
V1.4          ：45 44 | 00 0D | 00 01 | A1 | 17 | 00 02 | 00 0A    | 5B        ← 13 B、不转义、无帧尾
```

旧口径那次「`00 0A` 写成了 `00 09 01`」就是转义，多出来的 1 字节让线上比声明长 1；而 V1.4 里 `00 0A` 就是 `00 0A`。
**可执行结论：拿旧解析器读新设备 = 0 帧。** 判别一段字节是老还是新，只看**末字节**：`0x0A` 结尾（且长度 = `12 + N`）= 旧口径；无 `0x0A`、长度 = `11 + N` = V1.4。

| 症状 | 真实原因 | 怎么判断 / 怎么验 |
|---|---|---|
| 新设备一帧都解不出 | 解析器还在等帧尾 `0x0A`，或按 `12+N` 裁帧 | 打印「声明长度 / 实际剩余字节数 / 末字节」三个值，末字节不是 `0x0A` 就说明是 V1.4 |
| 偶发「丢一帧」 | 收方向按 `0x0A` 切分，而 `0x0A` 现在**不再**是帧界 | 接收侧禁止按 `0x0A` 切；只能「先读帧头 + 长度、再定长读 N 字节」 |
| 明明有人却没数据 | 用了旧口径的「双口径自适应」，把新帧当坏帧丢了 | 解析器只按 `11+N` 一种口径实现，另一种口径直接报错，不做静默兼容 |

### 2. `0x81` 是 9 字节单目标，且 Z 是无符号

| 字节 | 字段 | 类型 / 取值 |
|---|---|---|
| 1 | 延时有无人状态 | 0 无人 / 1 有人 |
| 2 | 无人 / 静止 / 运动 | 0 无人 / 1 静止 / 2 运动 |
| 3 | 静止 / 靠近 / 远离 | 0 静止 / 1 靠近 / 2 远离 |
| 4-5 | X 坐标 | 大端 **int16**（有符号，二进制补码），mm |
| 6-7 | Y 坐标 | 大端 **int16**（有符号），mm |
| 8-9 | Z 坐标 | 大端 **uint16（无符号）**，mm |

V1.4 删掉了 `0x13` 检测通道数量，所以 **`0x81` 没有「每通道」概念**：一条 `0x81` 就是一个目标，长度固定 9 B，
`tlv_len ≠ 9` 只可能是载荷异常，不是「通道数变了」。官方示例 `01 02 01 00 64 00 C8 05 DC` →
**有人 / 运动 / 靠近 / X=100 / Y=200 / Z=1500**；负值用例 `01 02 02 FF 9C 00 C8 05 DC` → X=**-100**、Y=200、Z=1500（`FF 9C` 按补码读是 -100，按无符号读会变成 65436）。

**可执行结论：步长钉死 9、`Z` 按无符号读。** 整帧长这样（`0x14 = 20 = 11 + 9`）：

```text
45 44 00 14 00 01 A3 81 00 09 01 02 01 00 64 00 C8 05 DC DC
```

### 3. 默认 5 s 上报 + 「触发有人后才上报」⇒ 无人期可能完全静默

| 参数 | 默认值 | 实际含义 | 风险 |
|---|---|---|---|
| `0x17` 上报频率 | 50 | 50 × 100 ms = **5 s** | 页面 5 s 才动一次，看起来像卡死 |
| `0x12` 闭锁时间 | 2 | 人离开后 2 s 内不允许重新判「有人」 | 调大到 60 s ⇒ 人走了灯还亮一分钟，被当成误判 |
| `0x24` 触发模式 | 0 | 正常运动触发 | 完全静止的人可能不产生触发（见下） |
| `0x1B` 触发使能 | 1 | 允许触发 | 设 0 ⇒ 雷达不再产生触发，看起来像设备坏了 |

**演示前必须做的两条**：`SET 0x17 = 10`（1 s 上报，否则 5 s 一次的刷新会让你以为链路不通）、`SET 0x18 = 1`（确认射频没被关）。
顺序是「`GET` 回读 → `SET` → 再 `GET` 确认」，页面把「回读 ≠ 设定」标红。

**真正的坑在语义上**：`0x17` 原文是「雷达**触发有人后**，每隔所设置的时间上报一次有无人状态」。也就是说「无人」这个状态**设备可能根本不发**——
人走空之后，流里可能一段时间**一个字节都没有**；上位机若按「收到帧且字段 = 0 才算无人」，界面会永远停在最后一帧的「有人」。

**可执行结论：上位机必须用超时推断，且静默推断不能断言「无人」。** 静默窗取 `max(3 × 0x17 周期, 8 s)`（8 s 是**下限**）：

| `0x17` | 上报周期 | 3 × 周期 | 静默窗 | 说明 |
|---|---|---|---|---|
| 50（出厂默认） | 5 s | 15 s | **15 s** | 15 s > 8 s，按 3 倍周期 |
| 10（演示推荐） | 1 s | 3 s | **8 s** | 3 s &lt; 8 s，**取下限 8 s，不是 3 倍周期** |

| 界面状态 | 判定条件 | 别写成 |
|---|---|---|
| 有人 | 收到帧且第 1 字节 = 1 | — |
| 无人 | 收到帧且第 1 字节 = 0 | 「没数据 = 无人」 |
| **无数据（可能无人，也可能有人但静止没被触发）** | 距上一帧 > 静默窗 | 「无人」「设备离线」「有人」——静默只说明没收到帧，三种都推不出来 |

**静默有两种原因，别只按一种处置**：① **真无人**——设备按「触发有人后每 X 上报」的语义停发，属正常；
② **有人但完全静止、没产生运动触发**——`0x24` 默认 0（正常运动触发）⇒ 人坐着不动时流里同样可以一个字节都没有。
第 ② 条最容易被自己的界面骗过去：按静默推断显示「无人」，**恰好把本文的卖点显示成反面，而且不报任何故障**。
所以静默期间只显示带「按静默推断」限定的文案 + 判定依据（超时推断 / 静默 X s），要断言「无人」必须等到一帧 `presence = 0`。

### 4. 设备 ID 默认已是 `EDQ163_VB`，但 V1.4 自己的示例仍回 `EDQ152_VB`

`0x02`（雷达模块信息，16 B）里：**1~9 B 设备 ID**（默认 `EDQ163_VB`）、**10 B 是逗号 `0x2C`**、**11~16 B 固件版本**（默认 `V2.0.0`）。
但 V1.4 §4 的第 2 组示例，模组回的却是 `EDQ152_VB,V2.0.0`（`… 45 44 51 31 35 32 5F 56 42 2C …`）——**协议自己和自己不一致**。

**可执行结论：不能靠 ID 认型号。** 一条能跑通的确认流程：

1. `GET 0x01` → 3 B：第 1 字节协议版本、第 2~3 字节厂商 ID（应为 `45 44` 即 `"ED"`）；顺带验证切帧——它的 Report 是 `45 44 00 0E 00 01 A2 01 00 03 00 45 44 C7`，**Value 里就有 `45 44`**；
2. `GET 0x02` → 16 B：第 10 字节必须是 `0x2C`，版本串（11~16 B）不为空；**读到 `EDQ163_VB` 或 `EDQ152_VB` 都不能当结论**，两个值在文档里都存在；
3. 一组**功能性回读**：`0x17` 频率、`0x12` 闭锁、`0x25` 挂高、`0x27` 检测范围、`0x29` 屏蔽区，能正确回读才说明支持 V1.4 命令集；`GET 0x13` 若还有效，说明对端是**旧固件**；
4. 看第一条上报帧的**形态**：`45 44` 开头、长度 = `11 + N`、末字节不是 `0x0A`、`0x81` 恰好 9 B ⇒ 按本篇口径解析。

**不能做的事**：用设备 ID 判断该按 9 B 单目标还是按「多通道」解析。ID 分不出来——新固件若沿用旧 ID 串，你会误判；能分出的是**帧形态**。

### 5. 别再找「50 B 单帧上限」了

V1.1 那句「雷达接收数据最长为 50 BYTE，超过 50 BYTE 的部分不会识别」**在 V1.4 里不存在**，整份协议没有任何单帧长度上限；
真要找上限，只有长度字段本身是 2 B（最大 65535）。
`0x29` 屏蔽区的 Value 是 `1 + 13 × N`（N = 屏蔽区个数 0~10），整帧 = `12 + 13N`：

| 屏蔽区数 N | Value 字节 | 整帧字节（11 + Value） | V1.4 能否一帧下发 |
|---|---|---|---|
| 1 | 14 | 25 | ✅ |
| 2 | 27 | 38 | ✅ |
| 3 | 40 | 51 | ✅（旧口径下这一帧是 52 B，早就超 50 B 发不出去了） |
| **10** | **131** | **142** | ✅ 工程师上位机就是这么发的 |

**旧文里「每帧最多 2 个屏蔽区、10 个只能分批下发」的推论作废**——它建立在 V1.1 的 50 B 假设上。
现在可以一帧发满 10 个；`SET 0x29` 的 Value 自带数量字段，**语义上最可能是「完整覆盖」而非「追加」**，但文档没写死，
所以还是要 `GET 0x29` 回读确认（判据见「待实测」表）。

## 我该选哪一套

同一块 EDK60、同一颗 EDV163 系列模组，站内现在有三套配方。**它们不是「同一个协议的不同展示」，而是三套固件 + 三套上位机口径**：

| 维度 | 人存（本篇，EDV163-N-03） | 水位（EDV163 吊装测距） | 挥手（EDV163 手势固件） |
|---|---|---|---|
| 串口流形态 | 二进制帧，**V1.4：`11+N`、无帧尾、不转义** | 二进制帧，**旧口径：`12+N` + 帧尾 `0x0A` + 字节转义** | **文本行**（`GESTURE: …`），混 `0x4544` 点云帧 |
| 波特率 | 256000（V1.4 固定，无波特率命令） | 256000 | 115200 |
| 主数据 | `0x81`：**固定 9 B 单目标**（人/静动/方向 + X int16 / Y int16 / Z **uint16**） | `0x81`：**7 B/通道**（含 `target_distance`） | `action` −2~2 + `target`/`x`/`y`/`z` |
| 要回答的问题 | 「有人吗、坐着还是动着、人在哪」 | 「水面多高、在涨还是在降」 | 「手往哪个方向挥」 |
| 选错会怎样 | 拿旧口径解析器读新设备 → **0 帧** | 拿 `11+N` 读旧帧 → 长度裁错、一直重同步 | 拿二进制解析器读文本行 → 一帧都解不出 |
| 站内依据 | 本文 | [水位案例](/blog/edk60-edv163-water-level) | [挥手案例](/blog/edk60-edv163-gesture) |

**同一型号不同固件/协议版本，口径会变，先认帧形态再写解析器。** 到手先抓一段原始字节：`45 44` 开头是二进制，
再看末字节是不是 `0x0A`（有 = 旧口径，无 = V1.4），最后数 `0x81` 的 `tlv_len` 是 9 还是 7；`GESTURE:` 开头则是文本行。选错口径不会报错，只会出垃圾数据。

## 已知限制

| 限制 | 现状 |
|---|---|
| **长稳与精度仍未验证** | 2026-11-19 首轮已上板打通（单点、约 3 分钟、33 帧）。帧率上限、坏帧率长期水平、检测范围/角度精度、响应延时、静止识别率、电流**仍然没有数据** |
| **坐标与角度精度未知** | `X/Y/Z` 是 int16/uint16 mm，但**毫米单位不等于毫米精度**；未做卷尺/十字标定，也未测角度分辨率 |
| **无人静默口径** | `0x17` 限定「触发有人后」上报，无人期间可能完全无字节；「无人」只能由超时推断，且静默≠无人 |
| **V1.4 与 V1.1 不兼容** | 帧长 `11+N` vs `12+N`、无帧尾 vs 有帧尾、不转义 vs 转义；同一份解析器不可能同时吃两种口径 |
| **`EDQ163_VB` / `EDQ152_VB` 文档内部矛盾** | 命令表默认值写 `EDQ163_VB`，§4 示例却回 `EDQ152_VB`；两个值都不能当型号结论 |
| **单目标、不做多人** | `0x81` 一条报文只给一个目标状态；多人场景里它代表「视野内的主目标」，不告诉你还有几个人 |
| **V1.4 无 `0x80` 能量帧、无 `0x1E` 调试模式** | 靠能量/距离门画图这条路已经断了；想要「活动随时间变化」，只能自己按 `0x81` 的坐标流累积成轨迹 |
| **`0x12` 的「0」语义未写死** | 协议只给 0~65535 s 范围与默认 2 s；`SET 0x12=0` 是「立即允许重新触发」还是「不闭锁」没写，见待实测 |
| **屏蔽区覆盖/追加语义不明** | 一帧能发 10 个，但多次 `SET 0x29` 是覆盖还是追加，文档没写 |
| **30 分钟强制清人可能误清** | `0x1D` 打开后，长时间静坐（看书、陪护、午睡）可能被强制判无人；默认关闭，别为「防呆」随手打开 |
| **侧装与吊装几何待定** | 产品页口径侧装 0.5~1.8 m，人存常见做法吊装 2.4~3 m 俯视；孰优要用「静坐 30 min 的误判次数」判定 |
| **`0xA9` ACK 未定义载荷** | 协议只给了 op 码，没定义载荷与状态码；收到只能当「已应答」，不能从中读参数 |
| **自学习命令未实测** | `0x20`~`0x23` 需要现场学习环境；协议只给了字段与取值，没写学习期间的人存表现，也未实测 |
| **浏览器限制** | Web Serial 只在 Chrome / Edge 89+ 可用，需 https 或 localhost；Firefox / Safari 不支持 |
| **不承担安全结论** | 人存是感知结果，不是安全联锁；不可用于安防报警、消防、生命监护、门禁安全联锁等有责任后果的场景 |
