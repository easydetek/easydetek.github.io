**「人还在不在」和「人动不动」是两个问题**，而便宜的存在检测大多只回答后一个：PIR（热释电红外）测的是红外辐射的**变化量**，
人一坐定、变化量归零，它就判「无人」——自习室、办公位、卫生间隔间的灯，正是在人坐着的时候自己灭掉的。
毫米波雷达看**微动与呼吸引起的胸廓起伏**（毫米级位移）：它的**设计目标**是——静止的人依然有回波、依然有周期性起伏，因此静坐也应被判为「有人」；**但这一点尚未实测**，是本文列在「待实测」里的核心项（判据见实施指南 表 B ⑪：静坐 10 min，`presence=1` 帧占比 ≥ 95%，`0x81` 到达间隔一并记录）。

**EDV163-N-03** 把这件事做成「一条报文说清」：主动上报 `0xA3 / 0x81`、**每通道 9 字节**，一次就给出**有人/无人 →
静止/运动 → 靠近/远离 → 目标 x/y/z 坐标（int16，mm）**；开调试模式后还会推 `0xA3 / 0x80`，把 **40 个距离门的运动能量 +
40 个距离门的静止能量**（每门 0~100）整包吐出来。

我们用 **EDK60 开发板**（ESP32-C6）把它桥到**芯片原生 USB**：模组串口字节**原样**搬到 USB，浏览器打开一个单文件网页，
就能看到「有人/无人」大字、40×2 条距离门能量柱与目标坐标——无 USB 转串口芯片、PC 端不装驱动、不上传任何数据。

> **⚠️ 验证状态（必读）**：这套链路**还没有在 EDV163-N-03 实物上跑过**，所以本文**不含任何实测数字**：
> 帧率、坏帧率、检测范围、距离/角度精度、检测延时、电流全部标着「待实测 + 判据」。
> 协议每一条都按《EDV163 替换 EDQ152 成品通用协议 V1.1》原文核对；示例帧是**按规则程序化生成/合成自测**的，
> **不是设备抓包**；凡由脚本或网页自测得出的结论，都写明「合成帧自测，非设备实测」。

## 场景需求

| 需求 | 说明 | 方案如何满足 |
|---|---|---|
| **静坐也要被感知** | 人坐着不动（看屏幕、开会、如厕）时不能判「无人」 | 雷达看微动与呼吸级起伏；`0x81` 第 2 字节把「静止」单列一档，不用靠运动量硬猜 |
| **非接触** | 卫生间、隔间、病房不适合装要被人碰的东西 | 60 GHz FMCW，**零接触**，不采集任何图像 |
| **无机械件、免维护** | 现场没人愿意擦探头、换电池、爬上去重新对准 | 无镜头、无运动部件、无易损件，**没有运动部件就没有机械磨损** |
| **单台覆盖一个工位或隔间** | 点位越少越好装、越好维护 | 一颗模组 + 一条 USB-C；检测范围（`0x27`）与检测高度（`0x26`）都能下发 |
| **免驱动接 PC 看数据** | 现场电脑常是受控环境 / 云桌面 | ESP32-C6 原生 USB CDC，插上就是串口 |
| **上位机可替换** | 客户已有自己的网关或平台 | 桥接固件**纯字节透传**（不解析、不组帧、不做转义）；协议公开，谁都能写上位机 |

**为什么这一档必须谈「状态机」而不是「触发」**：人存要回答的是「现在有没有人」这个**持续状态**，所以模组给的是一组时间参数——
`0x11`（检测延时）、`0x17`（上报频率）、`0x1C`（无人后仍允许存在检测的时间）、`0x1D`（30 分钟强制进入无人）。
它们不是可选调参项，而是**「人走了多久才算走」的定义**（默认值见工程点 3）。

## 方案构成

```text
EDV163-N-03 60 GHz 人存雷达模组（侧装或吊装，天线朝向被检测区）
   │  UART 256000 8N1（模组 TX → IO4，模组 RX ← IO5）
   ▼
EDK60（ESP32-C6）——纯字节双向透传：不解析、不组帧、不做转义、不代发命令
   │  芯片原生 USB CDC（免驱动）
   ▼
浏览器（单文件网页）：还原转义 → 按长度切帧 → 校验和 → 解 0x81（9 B/通道）/ 0x80（40+40 门能量）
```

| 环节 | 器件 / 技术 | 关键点 |
|---|---|---|
| 感知 | EDV163-N-03（60 GHz 人存雷达，协议 V1.1） | `0xA3/0x81`：**9 B/通道** = 有人 0/1 + 无人/静止/运动 + 静止/靠近/远离 + x/y/z（各 int16 大端，mm）；`0xA3/0x80`：80 B = 40 门运动能量 + 40 门静止能量，各 0~100 |
| 主控 | ESP32-C6（EDK60_VA V1.0） | UART1 与模组通信（**256000** 8N1），原生 USB 与 PC 通信，两路各自独立 |
| 连接 | 芯片原生 USB Serial/JTAG | 省掉 USB 转串口芯片与驱动；USB CDC 对波特率不敏感，填 256000 只为与线速对齐 |
| 供电 | PC 的 USB-C 口 | 3.3 V 单电源由板载 LDO 供，**不需要外部适配器**（峰值电流待实测，判据 &lt; 300 mA） |
| 上位机 | 单文件网页（Web Serial） | **默认只读**：连上只发 GET；写参数必须逐条确认、并等应答 |

两条与「看数据」直接相关的口径，先说清楚免得白折腾：

1. **`0x80` 很可能要开调试模式才有**：协议只写它「允许操作 = status」，没写触发条件，而 `0x1E`（调试模式）默认是 **0**。所以「40 门能量柱一条都没有」不等于桥坏了——**推断需要 `SET 0x1E=1`，待实测**。
2. **40 个距离门不等于 40 个等分点**：协议给的是「距离门 1~40」与最大检测距离 6000 mm，按 40 门铺满 0~6000 mm 推算**门宽约 150 mm**（文档没写门宽，属**推断**）；能量值是 0~100 的相对量，**不是 dB、不是 RCS**。

## 接线与安装

| 信号 | EDK60 侧 | 模组侧 | 说明 |
|---|---|---|---|
| 模组 TX → MCU RX | **IO4** | H3 排针 `T` 脚 | 数据入口（状态、能量、坐标全靠这条线） |
| 模组 RX ← MCU TX | **IO5** | H3 排针 `A` 脚 | 下发配置（`0x17` 频率、`0x11` 延时、`0x25` 挂高、`0x29` 屏蔽区） |
| 雷达电源使能 | **IO14**（高有效） | — | 上电后常高；丝印 `RADAR` 红灯 = 已上电 |
| 电源 / 地 | `3.3V_RADAR` / `GND` | `V`、`P` / `G` | 3.3 V 单电源，**不需要电平转换** |
| 串口参数 | **256000 / 8N1**，无流控，**大端** | — | 协议原文写「256000 固定」，但 `0x04` 默认值是 **4 = 115200**（见工程点 3） |

:::warning 模组必须插 H3，不要插 H4；禁止带电插拔
板上 H3 与 H4 两个 8 pin 排针**信号集合相同但顺序相反**：H3 = `RES A R T G V P`，H4 = `RES P V G R T A`。H4 的 `T` 脚与雷达电源
使能在同一侧的网络关系上，插 H4 会让电源与数据互相干扰，症状是「红灯亮着、却一个字节都没有」或「偶发丢帧」——最难查的那一类。
另外**禁止在雷达已上电（红灯亮）时插拔模组**，热插拔会同时打电源与 UART 两条线。
:::

| 项 | 侧装（产品页口径 **0.5~1.8 m**） | 吊装俯视（人存常见做法 **2.4~3 m**） |
|---|---|---|
| 姿态 | 装墙面/立柱，天线朝水平方向 | 装天花，天线朝正下方 |
| 对「静坐」 | 视线能照到躯干（胸腹起伏面最大），几何上更有利 | 只照到头顶与肩，呼吸起伏的投影面积小 |
| 遮挡 | 隔断、屏风、立柱会切扇区 | 天花板方向无遮挡，但桌面、吊柜会挡 |
| 坐标含义 | `x/y` 是水平面内位移，`z` 的物理含义待实测 | `z` 最可能 ≈ 离地高度（推断） |
| 主要风险 | 正面贴装时的近场盲区；远距离波束变宽 | 挂高与检测高度设错 → `z` 全错、扇区漏检 |

两种安装孰优**取决于检测范围的实测**，本文给不出结论（判据见「真实状态」最后一条）。

**`0x25`（挂高）与 `z` 的关系**：`0x25` 是 1200~5000 mm 的系统参数，而 `0x29` 屏蔽区的约束写的是 `0 < Z < 挂高`，说明 **`z` 的量程上限就是挂高**；
由此推断 `z` 从安装基准（地面）向上量、吊装时 ≈ 离地高度——这是**推断不是结论**，验证办法：蹲下/站起各采 30 s，看 `z` 是否跟着人高变化。
对照：站内 EDV11P 侧装案例的 `z` 恰好铺满配置的检测高度区间，但那份文档同样注明「未做绝对高度标定」。

## 关键工程点

### 1. 帧尾 `0x0A` 与字节转义：长度按「转义前」算

| 字段 | 字节 | 说明 |
|---|---|---|
| 帧头 | 2 | 固定 `45 44` |
| 长度 | 2 | **整包长度 = 12 + N**，N 是 value 的**转义前**字节数 |
| msgid | 2 | 序列号 `0~0xFFF0`，到顶回 0；**按 `(op, type)` 分组看连续性**，混着看会误判丢帧 |
| op | 1 | `0xA0` Get / `0xA1` Set / `0xA2` 被动上报 / `0xA3` 主动上报 / `0xA9` ACK |
| type | 1 | 命令字：`0x81` 上报数据、`0x80` 调试能量…… |
| tlv_len | 2 | value 的**转义前**长度 |
| 校验和 | 1 | 自 `45` 起至 value 末字节、**转义前**求和 mod 256 |
| 帧尾 | 1 | 恒为 `0x0A` |

转义表：`0x0A → 09 01`、`0x09 → 09 00`（**帧尾的 `0x0A` 不转义**，只有正文里出现才转义）。这两条同时把「长度」和「切帧」搞乱。

**可执行结论：组帧一律程序化，长度字段永远填「转义前」的数。** 拿最简单的 `SET 0x17 = 10`（上报频率 1 s）举例：

```text
45 44 | 00 0E | 00 01 | A1 | 17 | 00 02 | 00 09 01 | 5C | 0A
```

- value 逻辑上是 `00 0A`（2 B 大端，10 × 100 ms = 1 s），线上是 `00 09 01`；**声明 14 B（`0x000E`）、线上 15 B**——多出来的 1 字节就是转义；
- 校验和 `0x5C`：因为 `0x09 + 0x01 = 0x0A`，**转义不改变和值**，既不用「先还原再算」，也不用「加回来」。

| 症状 | 真实原因 | 怎么判断 / 怎么验 |
|---|---|---|
| 发出去的 SET 完全没回应 | 长度填成了线上字节数（15 而不是 14），设备当截断帧丢掉 | 同一份代码同时算「声明长度」与「实际字节数」，**不相等就报错**，不要靠眼睛数 |
| 上位机偶发「丢一帧」 | 文本日志的换行就是 `0x0A`，正好切断当前帧 | 接收侧**禁止按 `0x0A` 切分**；只能「先读长度、再定长读 N 字节」 |
| 载荷里的 `0x0A` 被当成帧尾 | 收方向没做转义还原 | 统计「还原的转义对数」：为 0 有两种可能——真的没触发，或根本没实现 |

文档在这里还自相矛盾，照抄示例会直接造坏帧：V1.0 修改记录写着「取消结尾的 `0x0A`」，但 V1.1 的帧格式表、通信约定与 4 组命令
示例（每组主机 + 应答，共 8 条）的帧尾全是 `0A`；而且 `0x17` 那条示例把 2 B 的 value 写成了 1 B 的形式（长度 `0x000D`、value 只写 `09 01`）。**以规则为准，不以示例为准。**

### 2. `0x81` 是 9 字节/通道，不是 7、也不是 8

站内已经有两份文档在讲 EDV163 的 `0x81`，口径并不一样，这是集成时最容易踩空的一步：

| 依据 | 每通道字节数 | 字段（首字节起） |
|---|---|---|
| **本篇《V1.1 替换 EDQ152》** | **9** | 有人/无人(1) → 无人/静止/运动(1) → 静止/靠近/远离(1) → x(2) → y(2) → z(2) |
| 站内水位指南《EDV163 串口通用协议》口径 | **7** | 通道号(1) + 有人(1) + 状态(1) + 方向(1) + 距离(2) + 角度(1)（该文档正文另有一处写「8 字节」，是笔误） |

**为什么这个差异会「藏起来」**：拿 7 B 的循环解 9 B 载荷，单通道（`tlv_len = 9`）时前 7 字节恰好是「有人/状态/方向/x/y」——
**值全对，只是 `z` 被丢掉、剩 2 字节当残尾忽略，一声不响**；一旦上报 2 通道（18 B），第 2 通道从第 8 字节起读，**整体错位 2 字节**，坐标变成垃圾值，依然不报错。

**可执行结论：步长钉死 9，并把口径显示在界面上。** 判据三条：`tlv_len % 9 == 0`；单通道时 `tlv_len == 9`；`tlv_len / 9`
与 `GET 0x13`（检测通道数量，1~4）回读值一致。注意 V1.1 的 `0x81` **没有单独的「通道数」字节**（第 1 字节就是有人/无人），
通道数只能从 `tlv_len` 或 `0x13` 得到——这正是「步长错了就静默出垃圾」的根源。

### 3. 默认 5 s 才上报，而且「触发有人后才上报」→ 无人期间可能完全静默

| 参数 | 默认值 | 实际含义 | 风险 |
|---|---|---|---|
| `0x17` 上报频率 | 50 | 50 × 100 ms = **5 s** | 页面 5 s 才动一次，看起来像卡死 |
| `0x11` 检测延时 | 10 | 目标消失后仍保持「有人」**10 s** | 人走了灯还亮 10 s，被当成误判 |
| `0x1E` 调试模式 | 0 | 推断：`0x80` 能量帧无输出 | 40 门能量柱一条都没有 |
| `0x02` 设备 ID | `EDQ152_VB` | EDV163 替换 EDQ152 的遗留 | 不能用来认型号（见工程点 4） |

**演示前必须做的两条配置**：`SET 0x17 = 10`（1 s 上报）、`SET 0x11 = 3`（3 s 保持）；顺序是「`GET` 回读 → `SET` → 再 `GET` 确认」，页面把「回读 ≠ 设定」标红。

**真正的坑在语义上**：`0x17` 原文是「雷达**触发有人后**，每隔所设置的时间上报一次有无人状态」。也就是说「无人」这个状态**设备可能根本不发**——
人走空之后，流里可能一段时间**一个字节都没有**；上位机若按「收到帧且字段 = 0 才算无人」，界面会永远停在最后一帧的「有人」。

**可执行结论：上位机必须用超时推断，并把三种状态分开显示；静默推断**不能**断言「无人」。**

| 界面状态 | 判定条件 | 别写成 |
|---|---|---|
| 有人 | 收到帧且第 1 字节 = 1 | — |
| 无人 | 收到帧且第 1 字节 = 0 | 「没数据 = 无人」 |
| **无数据（可能无人，也可能有人但静止）** | 距上一帧 > 静默窗 `max(3 × 0x17 周期, 8 s)` | 「无人」「设备离线」「有人」——静默只说明没收到帧，三种都推不出来 |

**静默有两种原因，别只按一种处置**：① **真无人**——设备按「触发有人后每 X 上报」的语义停发，属正常，正是本文要测的行为；② **有人但完全静止、没被运动触发**——`0x24` 默认 `0`（正常运动触发）+ `0x17` 原文「**触发有人后**每 X 上报」⇒ 人坐着不动时流里同样可以一个字节都没有。第 ② 条最容易被自己的界面骗过去：按静默推断显示「无人」，**恰好把本文的卖点（静坐也能感知）显示成反面，而且不报任何故障**。**界面处置**：静默期间显示带「按静默推断」限定的文案（页面实际写的是「无人（按静默推断）」）+ 静默窗与判定依据（超时推断 / 静默 X s），**不得写成设备判定的「无人」**；要断言「无人」必须等到一帧 `presence = 0`。**第 ② 条是待实测项**：静坐 10 min 看 `0x81` 到达间隔与 `presence=1` 帧占比（实施指南 表 B ⑪），实测前按「可能是人」保守处理。

**静默窗 = `max(3 × 0x17 周期, 8 s)`**（与实施指南、演示页、烧录页同一口径，8 s 是**下限**）：

| `0x17` | 上报周期 | 3 × 周期 | 静默窗 | 说明 |
|---|---|---|---|---|
| 50（出厂默认） | 5 s | 15 s | **15 s** | 15 s > 8 s，按 3 倍周期 |
| 10（演示推荐） | 1 s | 3 s | **8 s** | 3 s &lt; 8 s，**取的是下限 8 s，不是 3 倍周期的结果** |

判据：静置 10 min 统计「相邻帧最大间隔」，超过静默窗 ⇒ 静默确实存在；但**超窗 ≠ 无人**——原因 ① 与 ② 在流上长得一模一样，只能靠「静坐 10 min」的实测区分。

### 4. 设备 ID 仍然叫 `EDQ152_VB`：不能靠 ID 认型号

`0x02`（雷达模块信息，16 B）里：**1~9 B 设备 ID**（默认 `EDQ152_VB`）、**10 B 是 `,`（`0x2C`）**、**11~16 B 固件版本**（默认 `V2.0.0`）。
这两个默认值都是**占位**——读到它们既不能证明「这是 EDQ152」，也不能证明「版本已写入」（对照：站内挥手版模组自报 `ID0xFFFF`，同样是未写入状态）。

**可执行结论：用「回读能力」而不是「ID」认型号。** 一条能跑通的确认流程：

1. `GET 0x01` → 3 B：第 1 字节协议版本、第 2~3 字节厂商 ID（应为 `45 44` 即 `"ED"`）；
2. `GET 0x02` → 16 B：第 10 字节必须是 `0x2C`，版本串（11~16 B）不为空、且**不是** `V2.0.0`；
3. 一组**功能性回读**（`0x13` 通道数、`0x17` 频率、`0x25` 挂高、`0x27` 检测范围）：能正确回读，才说明支持 V1.1 命令集；
4. 看第一条上报帧的**形态**：`45 44` 开头且 `0x81` 的 `tlv_len` 是 9 的整数倍 ⇒ 按本篇口径解析。

**不能做的事**：用设备 ID 判断该按 7 B 还是 9 B 解析。ID 分不出来——新旧固件都可能报 `EDQ152_VB`；能分出的是 `tlv_len`。

### 5. 主机→模组单帧 ≤ 50 B，所以屏蔽区 `0x29` 每帧最多 2 个

协议原文：「雷达接收数据最长为 50 BYTE，超过 50 BYTE 的部分不会识别」。这条**只约束下行**（推论依据：上报的 `0x80`
帧本身就 92 B = 12 + 80；若 50 B 是全链路上限，`0x80` 永远发不出来）。`0x29` 的 value 是 `1 + 13 × N`，帧长被算死：

| 每帧屏蔽区数 N | value 字节 | 整帧字节（12 + value） | 是否 ≤ 50 B |
|---|---|---|---|
| 1 | 14 | 26 | ✅ |
| **2** | **27** | **39** | ✅ 单帧上限 |
| 3 | 40 | 52 | ❌ 超限，尾部字节不会被识别 |

10 个屏蔽区只能**分批**下发。这里有一条文档没写、必须实测的语义：**每次 `SET 0x29` 是「完整覆盖」还是「追加」？**
value 里自带数量字段，最可能的行为是「覆盖」；若真是覆盖，分批下发就只有最后一帧生效。

**可执行结论**：先按 2 个/帧发 5 帧，再 `GET 0x29` 回读区个数——**回读到 10 个 ⇒ 追加语义**（分批可行）；**只有 2 个 ⇒ 覆盖语义**（分批无效，得改成一次下发 2 个以内，并把限制写进文档）。先数帧长再发，别等设备静默丢帧。

## 我该选哪一套

同一块 EDK60、同一颗 EDV163 系列模组，站内现在有三套配方。**它们不是「同一个协议的不同展示」，而是三套固件 + 三套上位机口径**：

| 维度 | 人存（本篇，EDV163-N-03） | 水位（EDV163 吊装测距） | 挥手（EDV163 手势固件） |
|---|---|---|---|
| 串口流形态 | 二进制帧，帧尾 `0x0A` + 转义 | 二进制帧，同样有帧尾与转义 | **文本行**（`GESTURE: …`），混 `0x4544` 点云帧 |
| 波特率 | 256000（协议约定；`0x04` 默认 115200） | 256000 | 115200 |
| 主数据 | `0x81`：9 B/通道（人/静动/方向/xyz） | `0x81`：7 B/通道（含 `target_distance`） | `action` −2~2 + `target`/`x`/`y`/`z` |
| 要回答的问题 | 「有人吗、坐着还是动着、人在哪」 | 「水面多高、在涨还是在降」 | 「手往哪个方向挥」 |
| 选错会怎样 | 拿 7 B 解 9 B → 单通道「看似正常」、双通道静默错位 | 拿 9 B 解 7 B → 距离字段全错 | 拿二进制解析器读文本行 → 一帧都解不出 |
| 站内依据 | 本文 | [水位案例](/blog/edk60-edv163-water-level) | [挥手案例](/blog/edk60-edv163-gesture) |

**买之前确认「固件」，不是确认「型号」**：到手先 `GET 0x02` 读版本串，再看第一条上报帧长什么样——`45 44` 开头是二进制（再数 `tlv_len` 定 7 还是 9），`GESTURE:` 开头就是文本行。选错口径不会报错，只会出垃圾数据。

## 已知限制

| 限制 | 现状 |
|---|---|
| **未实机验证** | 全部上板用例未做（没有 EDV163-N-03 实物）。本文不含任何实测性能数字 |
| **坐标与角度精度未知** | `x/y/z` 是 int16 mm，但**毫米单位不等于毫米精度**；未做卷尺/十字标定，也未测角度分辨率 |
| **无人静默口径** | `0x17` 限定「触发有人后」上报，无人期间可能完全无字节；「无人」只能由超时推断 |
| **文档 5 处矛盾** | 帧尾 `0x0A` 去留、波特率 256000 vs `0x04` 默认 115200、转义未说接收方向、`0x81` 9 B vs 站内旧口径 7 B、`0x17` 触发语义——本文只给判据，不给「权威答案」 |
| **检测延时会让「人走了还显示有人」** | `0x11` 默认 10 s；演示前不改，现场一定以为误判 |
| **30 分钟强制清人可能误清** | `0x1D` 打开后，长时间静坐（看书、陪护、午睡）可能被强制判无人；默认关闭，别为「防呆」随手打开 |
| **侧装与吊装几何待定** | 产品页口径侧装 0.5~1.8 m，人存常见做法吊装 2.4~3 m 俯视；孰优要用「静坐 30 min 的误判次数」判定 |
| **`0x80` 触发条件不明** | 推断需 `SET 0x1E=1`；未实测前，能量柱可能是空的 |
| **距离门能量是相对量** | 0~100 的相对值，不是 dB、不是 RCS、不能跨设备比较；门宽约 150 mm 属推算 |
| **屏蔽区分批语义不明** | 每帧最多 2 个（受下行 50 B 上限约束）；「覆盖 vs 追加」文档没写，见工程点 5 |
| **型号识别不可靠** | `0x02` 的设备 ID 默认就是 `EDQ152_VB`、固件版本默认 `V2.0.0`；不能用它认型号（见工程点 4） |
| **单目标、不做多人** | `0x81` 每通道给一个目标状态；多人场景只代表「该通道视野内的主目标」 |
| **浏览器限制** | Web Serial 只在 Chrome / Edge 89+ 可用，需 https 或 localhost；Firefox / Safari 不支持 |
| **不承担安全结论** | 人存是感知结果，不是安全联锁；不可用于安防报警、消防、生命监护、门禁安全联锁等有责任后果的场景 |
